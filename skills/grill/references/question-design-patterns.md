# 出题方法论与深水区清单

---

## 第一部分：四种让通用知识失效的出题机制

### 机制 A：锚定私有细节

答案取决于候选人项目里的**具体数值或具体选择**。别人不知道他选了什么，所以只能泛泛而谈。

模板：
> "你这个 [组件] 的 [参数] 当时设的是多少？为什么是这个值而不是 [一个更大/更小的值]？如果设成后者，你那个场景下会先出什么问题？"

**为什么有效**：真做过的人记得这个值，且记得当初为什么调它——通常是因为踩过坑。没做过的人只能说"根据业务情况调整"。

**判断标准**：能给出具体数值 + 能说出调这个值的**触发原因**（"一开始设的 X，压测时发现 Y，才改成 Z"）。

### 机制 B：反事实推理

从他的具体实现出发，推导一个假设性改动的后果。需要同时掌握实现细节和业务场景才能推。

模板：
> "如果把你这个 [设计决策] 改成 [另一种做法]，在你那个 [具体场景] 下，最先出问题的会是哪个环节？"

**为什么有效**：通用知识能回答"这两种做法各有什么优缺点"，但回答不了"在你的场景里哪个先崩"——那需要知道他的瓶颈在哪。

### 机制 C：错误前提陷阱

题目中嵌入一个**听起来合理但实际错误**的技术前提。正确的回答是先指出前提有问题。

**为什么有效**：这是本方法论中最强的一招。面对权威提问者给出的前提，只有真正理解的人才敢质疑；而生成式工具倾向于接受提问者设定的前提并顺着往下答。

**使用纪律**：
- 陷阱必须是**技术性错误**，不能是文字歧义或表述不清；
- 如果候选人没识破，**要在追问时给出提示**（"你确定这个前提成立吗？"），给第二次机会——目的是测深度，不是设局；
- 记录"是否识破"作为关键评分项，但**未识破不等于不合格**，可能只是紧张或没多想。

### 机制 D：现场量级估算

让候选人用他项目里的真实参数当场算一个数量级。

模板：
> "按你说的 [QPS/数据量]，你这个 [数据结构/缓存] 一天大概占多少内存？"

**为什么有效**：需要真实参数（他知道）+ 工程常识（他得有）。编造过参数的人算出来的结果往往会和他之前说的指标自相矛盾。

**判断标准**：不要求精确，要求**数量级正确**且**推导过程合理**。答"大概 GB 级，因为每条约 XX 字节乘以 XX 万条"就是好答案。

## 第二部分：各方向深水区清单

深水区的通用规律：**教程讲 happy path，真实实践的痛苦全在异常路径上**——超时、重试、并发、故障、数据不一致、边界值。

### RAG / 向量检索

**深水区**：chunk 策略与召回质量的关系、embedding 的相似度度量选择、混合检索的分数融合、召回内容与 token 预算的冲突、评测集构建。

**示例题（含错误前提陷阱）**：
> "既然向量检索匹配的是语义，那 chunk 切得越小，语义就越聚焦，召回准确率应该越高。你们当时是不是也是往小了切？切到多少 token 的？"

**陷阱**：前提错误。chunk 过小会丢失上下文，且 embedding 模型对过短文本的表示不稳定；实践中存在一个与文档结构相关的最优区间，而非越小越好。

**正确回答应覆盖**：
- [ ] 指出"越小越好"不成立，并说明原因（上下文丢失 / 短文本 embedding 不稳定）；
- [ ] 给出自己项目的具体 chunk size 和 overlap 设置；
- [ ] 说明是怎么定下这个值的（最好是有对比实验，哪怕是粗糙的）；
- [ ] 提到文档结构对切分的影响（表格、代码块、标题层级不能乱切）。

**典型错误回答**："对，我们切到 128 token，越小越精确。" —— 顺着错误前提往下答，说明没做过切分策略的实验。

**追问**："那你怎么知道当前的切法比另一种好？评测集是怎么来的？"

---

### LLM Agent / 工具调用

**深水区**：上下文膨胀与压缩、工具调用失败的重试与**副作用幂等**、并发调用的依赖编排、循环终止条件、成本可观测性。

**示例题（含错误前提陷阱）**：
> "Agent 调工具失败的时候加个重试就行了——你们的重试次数设的几次？"

**陷阱**：前提遗漏了幂等性。对于有副作用的工具（发消息、写数据库、调用付费 API、下单），盲目重试会造成重复副作用。真做过 Agent 的人会立刻想到这一点。

**正确回答应覆盖**：
- [ ] 指出重试必须区分工具是否幂等；
- [ ] 说明对非幂等工具的处理（幂等键、执行前确认、只读重试）；
- [ ] 区分失败类型：网络超时（可重试）vs 参数错误（重试无用，需让模型重新生成参数）vs 权限错误（应直接终止）；
- [ ] 提到重试与上下文的关系——失败信息要不要放回上下文让模型自己修正。

**典型错误回答**："设了 3 次重试，加了指数退避。" —— 只答了通用重试策略，没意识到副作用问题。

### 推理引擎 / 推理服务调度（vLLM、SGLang、TensorRT-LLM 类）

AI Infra 岗位最高频、也最值得深挖的方向。简历上"参与推理引擎调度模块""推理性能优化"这类 claim 分量很重，必须能问到实处。

**深水区**：连续批处理（continuous batching）的调度粒度、显存压力下的抢占策略、KV cache 的分页管理与碎片、prefill 与 decode 的资源竞争、前缀复用的失效条件、吞吐与延迟的取舍。

**示例题（含错误前提陷阱）**：
> "推理引擎在显存快满、KV cache 分配不出新块的时候，是直接拒绝请求让它失败的吧？你当时在调度这块具体改了什么？"

**陷阱**：前提错误。主流推理引擎在显存不足时走的是**抢占**——把部分运行中请求的 KV cache 换出到内存（swap），或直接丢弃后续重算（recompute），请求会被暂停后恢复，而不是直接失败。这是调度器设计的核心机制之一，真改过这块代码的人会立刻纠正。

**正确回答应覆盖**：
- [ ] 指出前提有误，说明是抢占而非失败；
- [ ] 能说清 swap 与 recompute 的取舍（swap 占内存带宽、recompute 耗算力，短序列重算更划算）；
- [ ] 说出自己具体改动的位置（抢占策略、批次组装顺序、调度优先级，还是别的）；
- [ ] 能说明改动前后的行为差异。

**典型错误回答**："对，会返回失败，我们加了重试。"——顺着错误前提走，且"重试"不是这个问题的真实解法。

**追问**："显存实在腾不出来时，现在的策略是按什么顺序挑'牺牲哪个请求'的？这个选择对 P99 有什么影响？"

**另一道（机制 A + B）**：
> "prefill 和 decode 抢同一批 GPU 资源，长 prompt 的 prefill 会把正在 decode 的请求卡住。你们当时是怎么处理的？如果完全不处理，最先恶化的是哪个指标？"

**要点**：能区分 TTFT（首 token 延迟）与 TPOT（token 间延迟）受到的不同影响，能提到 chunked prefill 或分离部署等做法。答"没处理"也可以，前提是知道这个矛盾存在。

**判断提示**：这个方向答"我们没做到那一步"完全可以接受。关键是**知不知道问题存在**——知道但没做，和不知道有这回事，是完全不同的深度。

### 秒杀 / 高并发库存

**深水区**：Redis 与 DB 的最终一致性、扣减成功但后续失败的回滚、分布式锁的续期与误删、热点 key。

**示例题（含错误前提陷阱）**：
> "你们用 Redis 的原子扣减保证不超卖——既然 DECR 是原子操作，那超卖问题就彻底解决了对吧？那如果扣减成功之后，发 MQ 那一步失败了，会怎么样？"

**陷阱**：前半句的前提不完整。DECR 的原子性只保证单次扣减不并发冲突，但"扣减 + 下单"这个**复合操作**不是原子的；且 DECR 会扣到负数，需要额外判断。后半句直接把候选人推到真实痛点上。

**正确回答应覆盖**：
- [ ] 指出原子扣减只解决了并发扣减，不解决复合操作的一致性；
- [ ] 说明扣减成功但后续失败会导致**少卖**（库存被扣但订单没生成）；
- [ ] 给出自己的处理方案：本地消息表 / 事务消息 / 定时对账补偿 / 库存预占带超时释放；
- [ ] 提到 DECR 扣成负数的处理（用 Lua 脚本先判断再扣，或用 `DECR` 后判断结果为负则回补）。

**典型错误回答**："Redis 是单线程的，操作是原子的，所以不会超卖。" —— 停留在八股层面。

**追问**："你们的补偿任务多久跑一次？这段时间里这部分库存是锁死的还是可售的？"

### 分布式一致性 / Raft

**深水区**：持久化时机、Leader 上任的 no-op 日志、commitIndex 推进规则、线性一致性读、快照与日志压缩。

**示例题（含错误前提陷阱）**：
> "Raft 里 Leader 一定有最新的数据，所以读请求直接打到 Leader 读本地状态机就是强一致的。你们的读是这么做的吗？"

**陷阱**：前提错误，这是 Raft 最经典的坑。一个旧 Leader 在网络分区后可能**还不知道自己已被取代**，此时它本地的数据是陈旧的，直接读会读到过期值。正确做法是 ReadIndex 或 Lease Read。

**正确回答应覆盖**：
- [ ] 指出旧 Leader 问题——分区后的 stale leader 仍会响应读请求；
- [ ] 说明正确做法：ReadIndex（读前确认自己仍是 Leader，需一轮心跳确认多数派）或 Lease Read（基于时钟租约，性能更好但依赖时钟假设）；
- [ ] 说明自己项目做到了哪一步（**诚实地说"我们没做，直接读的 Leader"也是好答案**，前提是他知道这有问题）。

**典型错误回答**："对，Leader 有最新日志，直接读就行。" —— 说明只实现到课程测试通过的程度，没想过线性一致性读。

**判断提示**：这道题**答"我们没实现 ReadIndex"完全可以接受**，关键看他知不知道这是个问题。知道问题存在但没做，和不知道有问题，是完全不同的深度。

### RPC 框架 / Netty

**深水区**：粘包拆包、ByteBuf 的引用计数与堆外内存泄漏、EventLoop 上的阻塞操作、连接的优雅关闭。

**示例题（含错误前提陷阱）**：
> "Netty 是全异步的，所以在 handler 里做点耗时操作也不会阻塞其他请求。你们的业务逻辑是直接写在 handler 里的吗？"

**陷阱**：前提严重错误。同一个 EventLoop 线程服务多个 Channel，在 `channelRead` 里做阻塞操作会阻塞**该 EventLoop 上所有连接**。这是 Netty 使用中最常见的生产事故。

**正确回答应覆盖**：
- [ ] 指出 EventLoop 是被多个 Channel 共享的，阻塞会影响其他连接；
- [ ] 说明正确做法：业务逻辑提交到独立业务线程池，或用 `EventExecutorGroup`；
- [ ] 若说自己写在 handler 里了，能说明当时的业务确实是纯 CPU 的轻量操作，也算合理。

**追问**："你们的 ByteBuf 是怎么释放的？有没有遇到过堆外内存涨上去下不来的情况？" —— 引用计数是另一个必踩的坑。

### 微服务 / 分布式事务

**深水区**：Seata AT 模式的全局锁与脏写、服务拆分边界、链路追踪的采样、级联故障。

**示例题（含错误前提陷阱）**：
> "用了 Seata 的 AT 模式之后，分布式事务就跟本地事务一样用了，业务代码不用改。那如果有个不走 Seata 的服务直接改了同一张表的同一行，会发生什么？"

**陷阱**：前半句是 Seata 的宣传语，但 AT 模式的隔离性依赖**所有写操作都经过 Seata 的全局锁**。有旁路写入时，回滚时的"反向补偿"会基于错误的前镜像，造成脏写。

**正确回答应覆盖**：
- [ ] 指出 AT 模式靠 undo_log + 全局锁实现回滚，旁路写会破坏这个前提；
- [ ] 说明后果：回滚时用旧的前镜像覆盖，导致旁路写入的数据丢失；
- [ ] 提到 AT 模式是**读未提交**的默认隔离级别，需要 `SELECT FOR UPDATE` 才能获得读已提交。

---

### 模型微调 / 训练

**深水区**：数据泄漏、评测集独立性、灾难性遗忘、LoRA rank 的影响、loss 与实际效果的脱节。

**示例题（含错误前提陷阱）**：
> "你们微调之后 loss 从 2.1 降到 0.3，说明模型学得很好。这个提升在评测集上体现出来了吗？评测集是怎么划分的？"

**陷阱**：训练 loss 大幅下降常常是**过拟合**的表现而非学好了。且如果评测集是从同一批数据随机划分的，而数据本身有重复或高度相似的样本，就存在**数据泄漏**，评测指标会虚高。

**正确回答应覆盖**：
- [ ] 指出训练 loss 不能作为效果指标，需要独立评测；
- [ ] 说明评测集的划分方式，以及是否做了去重/去泄漏（按来源划分而非随机划分）；
- [ ] 提到有没有测过通用能力的退化（灾难性遗忘）；
- [ ] 最好能提到人工评测或业务指标，而非只看自动指标。

---

### 前端性能

**深水区**：具体指标项的区分（FCP/LCP/TTI/CLS）、虚拟列表的不定高问题、测量方法的可靠性。

**示例题（机制 A + D）**：
> "你简历写首屏优化了 60%。这个 60% 具体是哪个指标？用什么测的？在什么设备和网络条件下测的？优化前后各测了几次取的什么值？"

**这道题不带前提陷阱，但极有效**——因为真做过性能优化的人对这四个问题有现成答案（Lighthouse / 真实用户监控 / 具体机型 / P75），而数字是编的人会含糊在"就是加载变快了"。

**追问（反事实）**："如果只允许你保留其中一项优化措施，你会保留哪个？为什么它贡献最大？"

## 第三部分：跨方向的通用题型

### 指标口径题（对付所有 Metric Claim）

> "你说的 [指标] 提升 [X%]，baseline 是多少？这个改动上线的时候，同期还有别的改动一起上吗？你们是怎么把这部分收益归到这个改动上的？"

**为什么有效**：归因是所有指标的死穴。真做过 A/B 或灰度的人能说清；数字是包装出来的人答不出"怎么归因的"。

**判断**：能说出"做了灰度对比"或诚实说"没法完全隔离，这是整体效果"都是好答案。**后者尤其好**——说明他知道归因的难处。

### 个人边界题（对付所有 Ownership Claim）

> "这个项目当时团队几个人？除了你还有谁在做？如果现在让你们组另一个人来讲这个项目，他会说自己负责的是哪部分？"

**为什么有效**：第三个问句很难绕过——它要求候选人从**别人的视角**描述分工，编造的人很难保持一致。

**判断**：能清晰划出边界、并且对同事的工作有具体了解，是真实参与的强证据。

#### 强角色词五问（遇到 Owner / 主导 / 0→1 / 核心作者 / 架构师 / 负责人 时逐条问）

这五问覆盖了归属主张的全部要素，建议按顺序问完：

1. **谁授予或分配了这个角色？**（正式任命还是自我描述）
2. **实际负责哪个子系统？**（边界在哪）
3. **哪些决策是由你本人提出的？**（决策权）
4. **哪些产物通过了评审并进入生产？**（"做了"与"上线了"的区别）
5. **哪个结果可以归因于个人，而不是团队？**（成果归属）

**第 4 问最有价值**——它把"做过"和"上线了"分开，而这正是包装最容易拉伸的地方。

**配套原则：要产物，不要口才。** 现代简历包装会专门帮候选人把架构讲清楚，所以**讲得清楚不证明参与了实现**。对这类 claim，应要求五类产物之一：本人署名的设计文档、对应的 PR/commit、本人写的测试、参与处理的线上事件、主持的评审记录。

**判断提示**：
- 讲不清架构 → 弱信号，可能只是紧张，不宜据此下结论；
- 讲得非常清楚但拿不出任何产物 → 这才是需要记录的落差。

### 失败复盘题（对付所有经历）

> "这个项目做下来，有没有哪个决策后来发现是错的？如果重做一遍，你会改什么？"

**为什么有效**：真实项目**必有**做错的地方。答不出任何失败的人，要么没深度参与，要么在回避。

**判断标准**：
- 好答案：能说出一个具体的技术决策失误，及其代价和修正过程；
- 弱答案："时间安排上可以更好""沟通可以更多"——这是通用套话；
- **警示**：这道题的区分度很高，但答不上来**也可能只是没准备过这个角度**，不宜单独作为负面依据。

## 第四部分：出题自检清单

出完题后逐条检查，任何一条不过关就重出：

1. □ 题目锚定了简历上的**具体一条 claim**，而不是通用技术问题？
2. □ 答案依赖候选人项目的**私有细节**，通用知识答不出来？
3. □ 埋的坑是**技术性**的，不是文字游戏？
4. □ 真正做过的人**确实能答出来**（不是无解题）？
5. □ 参考答案具体到**非该领域专家的面试官也能判断对错**？
6. □ 写了**"答不上来不说明什么"**，防止面试官过度解读？
7. □ 难度**匹配岗位职级**（没给校招生出资深架构题）？
