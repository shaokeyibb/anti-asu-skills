# 时间线自洽性核验

时间是简历里最难伪造得天衣无缝的维度。经历可以润色、指标可以模糊、技术可以堆砌，但**时间是刚性的**——一个人不能同时出现在两个地方，一项技术不能在发布之前被使用。

因此时间线核验是本工具箱中**唯一能稳定产出 `直接矛盾` 级结论**的方法。

---

## 零、开始之前：先确认当前日期

**这是第一步，不可跳过。** 多条核验规则依赖"现在是什么时候"才能正确执行：

| 规则 | 依赖当前日期做什么 |
| --- | --- |
| 专利 18 个月未公开期 | 判断"查不到"是正常的未公开期，还是确实不存在 |
| 证书有效期 | 判断该认证是否已过期 |
| 论文录用与见刊的时滞 | 判断"已录用未见刊"是否合理 |
| "至今""在职"类表述 | 计算实际时长 |
| 竞赛榜单下线 | 判断赛事年代久远是否解释了查不到 |

**没有确认日期就执行这些判断，最典型的后果是把"专利处于正常未公开期"误判为疑点**——这是一个纯粹由流程疏忽造成的、对候选人不利的错误。

确认方式：从对话上下文中获取当前日期；上下文中没有时，直接询问用户，或用 `date` 命令读取系统日期。**不要凭训练数据推测当前是哪一年。**

---

## 一、构建时间轴

把简历中所有带时间的条目提取出来，统一归一化为 `[起, 止]` 区间：

| 条目类型 | 常见时间信息 | 注意事项 |
| --- | --- | --- |
| 教育 | 入学—毕业 | 区分全日制 / 非全日制 / 在职，这决定了能否与工作并存 |
| 工作 / 实习 | 入职—离职 | 区分全职 / 兼职 / 远程 / 日常实习 |
| 项目 | 项目起止 | 注意项目可能横跨多段任职 |
| 开源贡献 | PR 提交/合并时间 | 可从 GitHub 精确到分钟，是最强的交叉验证源 |
| 论文 | 投稿 / 录用 / 发表 | 三个时间点不同，简历常只写一个 |
| 竞赛 | 报名 / 决赛 / 获奖公布 | 官方赛程通常公开可查 |
| 证书 | 考试 / 颁发 / 有效期 | 多数有官方查询入口 |

**归一化陷阱**：简历常用"2023.3—至今""2023 年"这类模糊表述。模糊时间不是问题，但在核验时要按**最宽松的解释**处理（即假设候选人说的是真的），只有在最宽松解释下仍然冲突，才算冲突。

---

## 二、四类冲突

### 2.1 硬冲突：物理不可能（可达 `直接矛盾`）

两段**排他性**经历的时间区间重叠。排他性指的是二者按其自身定义无法并存：

- 两段不同公司的**全职**工作/实习时间重叠；
- 声称在 A 地长期驻场，同期又有 B 地的线下履职记录。

**判定要求**：
- 必须两段都明确标注为全职/排他性质。"实习"若未注明日常实习还是全职实习，不能直接判冲突——日常实习（每周 2—3 天）与在校完全可以并存。
- 远程工作、兼职、顾问、外包等形式天然可并存，不构成冲突。
- 时间精确到月时，边界月份的重叠（如 A 到 2023.06，B 从 2023.06 开始）**不算冲突**——很可能就是无缝衔接。

#### ⚠ 在读期间的全职实习：**不是冲突**

**在校时间与全职实习重叠，是正常且普遍的，绝不能判为冲突。** 这是本文件最容易被误用的一条，必须显式排除：

- 国内硕士（尤其专业硕士）在研二、研三课程修完后全职实习，是**主流做法**；
- 本科生在大四、毕业设计阶段全职实习同样常见；
- 许多培养方案本身就要求或鼓励企业实习；
- 博士生在企业做全职研究实习也是常规安排。

因此，"全日制在读 2023.09—2026.06"与"全职实习 2024.03—2024.11"的重叠，**在报告中根本不该被提及**，更不能计入疑点。

只有在满足以下**全部**条件时，在校与工作的重叠才值得记为**软冲突（疑似）**——注意是软冲突，不是硬冲突：

- 重叠发生在有明确课程与考勤要求的学段（如本科低年级、研一课程期）；
- **且**两地相隔远，无法通勤，也不属于远程；
- **且**候选人未做任何说明（如休学、交换、培养方案允许）。

即便三条全部满足，仍只能是"疑似"，因为休学、网课、弹性学制、课程免修等解释都可能成立，且这些属于个人学业安排，不宜深究。

只有在排除以上所有合理解释后，才可标记为 `直接矛盾`，且报告中必须写明"已排除 XX、YY 解释"。

### 2.2 硬冲突：因果倒置（可达 `直接矛盾`）

简历声称在某时间点使用了当时尚不存在的技术。这是最干净的可判定类型，因为技术发布时间是公开、客观、可独立验证的事实。

核验步骤：
1. 提取简历中带明确时间的技术使用声明；
2. 查证该技术/框架/模型/规范的首次公开发布时间（官方 changelog、GitHub release、论文发表日期）；
3. 若使用时间早于发布时间，且差距超过合理误差（如超过 3 个月，排除内测/预览版可能），标记 `直接矛盾`。

**必须排除的合理解释**：
- 该技术有内测、预览版、早期分支，候选人可能有提前访问权限；
- 候选人所在公司是该技术的开发方或早期合作方；
- 简历时间标注笼统（如只写年份），实际可能落在发布之后；
- 技术名称在发布前后有变更，候选人用了新名字描述旧事物。

报告中必须列出该技术的公开发布时间及其来源链接。

### 2.25 硬冲突：0→1 的起点重定义（可达 `直接矛盾`）

**手法**：把"在已有系统上做重构/演进"表述为"从 0→1 建立"。

这是包装方法论中的明确技巧——其正向规则是"`0→1` 只用于新建闭环，优化存量系统时应改用 `X→Y` 演进箭头"。违反这条规则时，就产生了一个**可用时间戳验证**的矛盾。

**核验步骤**：

1. **先问"0"指什么**：新服务？新训练链路？新策略节点？还是整个产品？范围不同，结论完全不同。
2. **查候选人加入前，该能力是否以任何形式存在**。证据源：
   - 加入日期之前的提交记录；
   - 旧版本文档、产品发布公告、更新日志；
   - 该功能的早期版本截图或存档页面。
3. **判定**：
   - 若加入前**已存在规则版/原型版/早期实现**，而简历暗示**产品级从绝对零开始** → **可达 `直接矛盾`**（有客观时间戳）；
   - 若"0"指的是**新的策略模块或新链路**，而该模块确实是新建的 → **成立**，不是问题。

**这是少数能真正达到 `直接矛盾` 的模式**，因为"该能力此前是否存在"有客观、公开、带时间戳的记录。

**必须排除**：
- 候选人所指的"0"确实是某个新增子模块（多数情况如此）；
- 旧版本是完全不同的技术路线，重写等同于新建；
- 简历表述笼统，未明确指向产品级。

**正确的替代表述**：`规则原型 → LLM Workflow 架构重构`、`Fixed Workflow → ReAct 演进`——即 `X→Y` 箭头。

### 2.3 软冲突：强度不可能（只能疑似）

同一时间窗内声称的活动总量超过合理精力上限。例如某 6 个月区间内同时声称：

- 全职实习（每周 40 小时）；
- 全日制在读并修满学分；
- 主导两个个人项目从 0 到 1；
- 高频开源贡献；
- 发表一篇论文。

**这类判断永远只能是 `疑似`**，因为：
- 精力上限因人而异，确实存在超高产出的个体；
- 简历上的"项目"可能是同一份工作的不同切面，重复计入；
- 论文可能是更早工作的滞后发表；
- 开源贡献可能是小量的、碎片时间完成的。

正确用法：不是拿它下结论，而是**把它转成面试题**——"你在 2023 年上半年同时在做实习、毕设和这两个开源项目，能讲讲当时是怎么安排时间的吗？"真实经历者能自然讲出取舍与妥协，编造者往往会给出一个过于完美的答案。

### 2.4 软冲突：叙事空洞（只能疑似，且极易误伤）

两段工作之间的空窗期被一个时间跨度长、内容描述虚、无任何可核验痕迹的"个人项目"填充。

**极强的误伤警告**：职业空窗是完全正常的——健康问题、家庭照护、备考、休息、创业失败、行业裁员。**空窗本身绝不能成为负面结论**，也绝不应在报告中要求候选人解释空窗原因（这在很多地区涉及就业歧视）。

这一条只在极窄的条件下适用：候选人**主动**用一个项目填补了空窗，而该项目在核验中呈现出虚构特征（无代码、无产出、描述与技术常识矛盾）。此时问题在于**那个项目的真实性**，而不在于空窗。报告应针对项目本身，完全不提空窗。

## 三、GitHub 时间戳作为交叉验证源

如果候选人提供了 GitHub，其提交时间戳是简历时间线最有力的交叉验证材料，因为它精确、公开、且难以事后伪造（虽然 commit date 可被篡改，但 PR/issue/comment 的平台时间戳不可改）。

可交叉验证的点：

- **任职期间的活跃度模式**：声称在某公司全职期间，GitHub 在工作日白天是否有大量对**其他项目**的提交？（注意：这不必然有问题——很多公司允许开源工作，也有人午休/摸鱼提交。只有量级极大时才值得追问。）
- **项目声称时间 vs 仓库实际时间**：简历写项目 2023 年做的，仓库首次 commit 却在 2025 年求职季前一个月。
- **突击完善痕迹**：仓库长期无活动，在投递季前集中出现大量 commit（补 README、补测试、补注释）。**这不是造假**——求职前整理项目是完全正当的行为。但如果整个项目的实质代码都是在那一周内产生的，而简历声称它做了一年，就构成矛盾。

**时区陷阱**：GitHub 显示的时间取决于时区设置。做跨时区判断（如"工作日白天"）前必须确认时区，否则极易误判。

## 四、输出格式

时间线核验的结果建议以文本时间轴呈现，冲突点显式标注：

```
2022 ─────────── 2023 ─────────── 2024 ─────────── 2025
      │
      ├─ 教育：XX 大学 硕士（全日制）  2022.09 ──────────────── 2025.06
      │
      ├─ 实习：A 公司 [全职]  2023.03 ─── 2023.09
      ├─ 实习：B 公司 [全职]  2023.06 ─── 2023.12
      │                          ▲
      │                          └── ⚠ 硬冲突：两段全职实习重叠 2023.06—2023.09
      │
      ├─ 项目：XX 系统（声称使用 技术T）  2023.01 ─── 2023.08
      │                                        ▲
      │                                        └── ⚠ 因果倒置：技术T 首次发布于 2024.05
      │
      └─ 开源：3 个 PR  2025.07（投递季前一个月，集中提交）
```

每个标注的冲突下方，必须跟一段"已排除的合理解释"说明，以及结论档位（`直接矛盾` / `部分属实` / `疑似`）。
