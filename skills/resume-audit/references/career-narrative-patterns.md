## 使用前必读：两条防止误判放大的规则

### 规则一：不要重复计分

本文件中的 1.1（模板化句式）、1.4（集体成果个人化）、3.1（名词堆砌）在表面特征上有重叠——"一段经历里塞了很多内容且每条都很强"可能同时命中三节。

**同一个现象只能归入最贴切的一类，计为一个疑点。** 把它同时写成三条"疑似"，会人为把一个问题放大成三个，严重扭曲报告给面试官的观感。

归类参考：
- 问题在**句式节奏整齐、缺乏真实工作的不均匀感** → 1.1；
- 问题在**系统规模与个人角色不匹配** → 1.4；
- 问题在**技术名词数量多且跨越多个技术层次** → 3.1；
- 拿不准时选一个，在报告里说明"该现象也可从 X 角度解读"，但**只记一条**。

### 规则二：阈值按单段经历计算，不按整份简历

本文件中的比例阈值（如"80% 以上条目同构"）**以单段经历为分母**，不是整份简历。

原因：整份简历合并计算会被条目数最多的那段经历主导，掩盖分布差异。而且只有 1—2 条要点的经历天然谈不上"同构"，把它计入分母只会稀释信号。

具体做法：
- 逐段经历分别统计，**只统计条目数 ≥ 3 的经历**（少于 3 条无统计意义）；
- 在报告中按段呈现，如"A 公司 3/3 条同构，B 公司 2/5 条同构"；
- 判断整体倾向时看**有多少段经历呈现高同构**，而不是把所有条目混在一起算一个总比例。

## 一、包装工具的产出特征

市面上已有成体系的简历包装工作流（含 AI 驱动的技能包），它们的典型做法是把真实但平淡的工作，按固定模板重写成招聘方爱听的叙事。了解它们的产出规律，是识别的第一层。

### 1.1 四段式句式模板

包装工具最常见的重写公式是：

```
动作 → 系统能力 → 业务价值 → 结果证据
```

产出的句子长这样：

> 设计并落地统一配置中心的热更新链路，支撑上层业务在不重启的前提下动态调整策略，降低发布频次，配置变更平均生效时间从分钟级降至秒级。

单看这句话没有任何问题——它可能 100% 属实。**问题在于整份简历的每一条要点都严格遵循这个节奏**：动词开头、中段接系统能力、尾部必挂一个数字。

**识别信号**（按单段经历统计，见开头"规则二"）：
- **单段经历内** 80% 以上的要点条目结构完全同构，长度接近（如都在 40—60 字），且该段条目数 ≥ 3；
- 每条都以强动词开头（设计/主导/落地/重构/优化/攻克），几乎没有"参与""协助""跟进"这类真实工作中占多数的动词；
- 每条结尾都有量化结果，无一例外——真实工作中大量任务是没有干净指标的。

**为什么这是信号**：真实简历的经历密度是不均匀的。有的项目讲得出细节，有的只能一笔带过；有的有数据，有的只有定性结果。整齐划一的节奏说明经历经过了统一的"格式化"，而格式化过程中最容易丢失的就是事实边界。

**如何验证**：面试时挑最不起眼的一条要点追问细节。包装过的简历往往在"最强的两三条"上准备充分，而在被拉平的次要条目上一问就穿。

### 1.2 岗位定向的"稳妥版 / 进取版"

包装工作流常为同一段经历生成两个强度版本：稳妥版如实描述，进取版拔高定位并"待补证据"。如果候选人直接投出了进取版而没有补上证据，简历就会呈现出**定位强度远超证据密度**的状态。

**识别信号**：
- 简历顶部的自我定位（如"AI 基础设施工程师""分布式存储方向"）与下方经历的实际内容存在层级落差——定位是架构层，经历是业务开发层；
- 同一份简历投递不同岗位时，经历描述的技术侧重点发生漂移（如果能拿到多版）；
- 出现"深度参与""持续投入""长期关注"这类**强度词但无边界**的表述。

### 1.3 小贡献的宏大叙事

这是最需要警惕，也最容易误伤的一类。包装工作流会明确教人把微小的真实贡献重写成体系化叙事：

| 真实动作 | 包装后表述 |
| --- | --- |
| 修了几个 README 错别字 | 跨项目文档质量治理 |
| 修复了一处失效链接 | 开发者体验优化 |
| 在 3 个仓库各提了 1 个小 PR | 多项目开源协作闭环 |
| 提交的 PR 还没被合并 | 深度参与社区共建 / 开源协作中 |
| 给项目提了个 issue | 推动社区问题发现与闭环 |

**关键判断**：这些小贡献**本身是完全正当且值得鼓励的开源行为**，绝不应因为"小"而被贬低。问题只出在**表述与实际的落差**上：

- 写"为 XX 项目贡献文档修正" → **完全没问题，如实描述**；
- 写"XX 项目 Contributor" → **灰色**，技术上成立（确实进了贡献者列表），但会让人误解贡献量级；
- 写"XX 项目核心贡献者 / 参与 XX 核心模块设计" → **明确夸大**，需要作为重点核验项。

**核验方法**：不看 PR 数量，不看仓库知名度，**逐个打开 PR 看实际 diff**。判断标准是改动的实质内容，而不是它落在哪个仓库里。

### 1.35 措辞强度解码表 —— 最高价值的单条工具

公开的简历包装方法论中，有一条**明确的映射规则**：根据原始材料里的说法强度，选择对应的简历措辞。把这个映射**倒过来读**，就得到一张解码表——从简历上的措辞，反推原始材料大概率写了什么。

| 简历上出现 | 原始材料大概率是 | 面试该问 |
| --- | --- | --- |
| `XX 模块 Owner` / `端到端链路 Owner` / `从 0→1` | **独立负责** | "0"具体指什么？谁授予的？ |
| `策略架构 Owner` / `方向负责人` | **主要负责**（意味着有其他人共同承担） | 还有谁一起做？你的边界到哪里？ |
| `系统级共建者` / `核心参与者` | **参与推进 / 共建** | 你具体交付了哪个子模块？ |
| `当前方向` / `当前聚焦` / `规划中` / `探索` | **尚未落地** | 上线了吗？现在什么状态？ |
| `核心作者之一` / `核心成员之一` / `主要贡献者之一` | **对冲式表述**，见下 | 一共几个人？你是哪一部分？ |

#### 对冲式限定词："之一"

`核心作者之一` 是一种**双向对冲**的写法，值得单独识别：

- **对候选人**：万一被追问，"之一"提供了退路——从未声称是唯一的核心作者；
- **对读者**：视觉上"核心作者"四个字仍然完整呈现，"之一"极易被略读跳过。

**核验纪律（重要）**：

- **"之一"本身完全正当**。多人共同主导一个项目是常态，如实写"之一"恰恰比省略它更诚实。**不得因为出现"之一"就给负面判定。**
- 真正要核验的是"之一"的**分母和自己的位置**：一共几位核心作者？名单在哪里？该候选人负责的是哪一块？
- 若分母很大（如实际有十几位同等身份者），而简历的上下文暗示核心圈层很小，这才构成落差。
- 若拿不到分母 → `公开检索无支持` 或 `结构性不可公开核验`，不要归入「疑似」。

**核心洞察（反直觉，务必记住）**：

> **Owner 前面的修饰词越花哨，底层来源越弱。**

裸的 `Owner` 对应"独立负责"；而 `策略架构 Owner` 只对应"主要负责"。更关键的是——**`核心参与者`、`系统级共建者` 里的"核心"二字，在这套体系里恰恰标记的是最弱的一档**（"参与"的加冕词）。

**同理，限定词才是真实 Scope，Owner 只是修饰。** "轨迹合成模块 Owner"的信息量全在"轨迹合成模块"上。反过来推论：**一个不带限定词的裸 `Owner` 比带限定词的更可疑**——按这套方法论，写不出限定词说明找不到可主张的最小闭环。

**关于"当前聚焦/规划中"的特殊纪律**：这类措辞是候选人在**诚实标记"这件事还没落地"**。核验时：
- **不把它算作已交付成果**；
- **也不把它算作疑点**——它是诚实信号，不是可疑信号。

特别注意不要因为这类条目"说不出具体成果"而误判为叙事空洞（见 [timeline-consistency.md](timeline-consistency.md) §2.4 对该误判的警告）。

### 1.4 集体成果的个人化

**识别信号**：
- 描述的系统规模（日均千万请求、服务全公司）与候选人的职级、司龄、团队规模不匹配；
- 通篇没有出现团队、协作、上下游、评审等词，仿佛整个系统由一人完成；
- 用"我们"和"我"混用且边界模糊，读完说不清他到底做了哪部分。

**注意**：候选人在大系统里只负责一小块，是绝对正常的。问题在于简历是否让人误以为他负责整体。面试时一问"这个系统当时团队多少人，你负责哪个模块"即可澄清。

### 1.55 版式层面的暗示（不是文字问题，是排版问题）

有些落差不在句子里，而在**版面结构**里。这类形态在逐句阅读时容易漏掉，需要专门看一眼整体布局。

#### A. 项目指标与个人职责的视觉绑定

**形态**：把项目的 star / fork / 下载量 / 用户量作为**项目标题行的一部分**排版，紧接着下一行就是"我的职责"。

```
github.com/org/project  ⭐ 76k stars · 10.3k forks
· 项目简介：……
· 我的职责：作为 XX，主导 YY
```

**为什么值得记录**：文字上没有任何一句声称这些 star 属于个人——**每个字都是真的**。但版面把"76k"和"我的职责"放在了同一个视觉单元里，读者的默认归因是把二者关联起来。

**核验方式**：与 §2.3（开源指标归属混淆）同源，但触发点是版式而非措辞。核验时把项目指标和个人贡献**显式拆开**，分别核实。

**必须注意**：
- **这不是造假**。标注项目的公开指标是常规做法，很多规范的简历都这么写；
- 结论上限是"建议面试时明确区分项目规模与个人贡献范围"，**不得记为疑点**；
- 只有当候选人在**口头或其他表述中**把项目指标说成个人成果时，才构成实际落差。

#### B. 头衔前置到身份行

**形态**：把开源社区头衔（Committer / Maintainer / PMC）与联系方式排在同一行，紧邻姓名和 GitHub 链接：

```
github.com/username（X 项目 Committer | Maintainer of Y）
```

**为什么值得记录**：放在联系方式行的内容，读者会当作**身份属性**（像"电话""邮箱"一样是既定事实）来读；而放在经历栏里的同一句话，读者会当作**待核实的主张**来读。位置改变了阅读预期。

**核验方式**：把它当作**主张**处理，不因为它出现在身份行就跳过。按 [../../credential-check/SKILL.md](../../credential-check/SKILL.md) 的"开源社区身份"一节核对公开名单，并注意 Contributor / Committer / Maintainer / PMC 是**层级完全不同**的身份。

**必须注意**：如果头衔属实，写在哪里都是候选人的自由，**排版位置本身不构成任何问题**。这一条只是提醒核验者**不要因为版面位置而降低核验强度**。

### 1.6 自证循环 / 多平台重复 —— **对本技能包尤其重要**

**手法**：同一个自我授予的角色，在多个自有渠道重复发布——个人博客写自己是核心作者、GitHub profile 写核心作者、个人主页写核心作者、社交平台简介写核心作者。搜索结果看起来像多方证实。

**为什么这对我们特别危险**：本技能包有 `github-audit`、`blog-check`、`credential-check` 三个独立的外部核验入口。如果三个入口各自查到"候选人自称核心作者"，报告会呈现为**三个维度都提到了这一点**——读起来像三重佐证，**实际只有一个来源：候选人自己**。

**必须遵守的规则**：

> **统计独立来源的数量，不统计出现次数。**

判定独立性：
- 候选人自己控制的渠道（个人博客、个人主页、profile、社交账号、自述、简历）—— **无论出现在多少处，都只算 1 个来源**；
- 独立第三方（项目官方名单、权威数据库、他人撰写的报道、平台生成的客观记录）—— 各算 1 个来源。

**在汇总报告时，必须显式标注每条证据的来源归属**，避免自述被重复计入。

### 1.7 社交邻接转技术授权

**手法**：把与维护者的互动、获得的点赞与回复、共同出现在某个 issue 或活动中，当作技术权威或联合开发的证据。

**重要前提**：**社交互动与建立信任本身完全正当**，是开源社区的正常运作方式，绝不应被贬低或当作负面信号。

问题只在于把"认识谁"表述成"实现了什么"。核验方式：查正式角色与交付产物，不看社交关系密度。

### 1.8 术语邻接（工种覆盖）

**手法**：因为工作发生在某个方向的团队里、数据管线附近或模型产品周边，就把实际是前端、数据处理或运营的任务，统称为该方向的工程（如统称为 `AI Infra`）。

这是 §3.1「名词堆砌」的一个更锋利的变体——**不是名词堆得多，而是用所在团队的方向标签覆盖了个人的实际工种**。

> ⚠️ **这是本技能包最容易漏掉、且漏掉后果最严重的一条。**
>
> 因为它无法靠读简历发现——简历里每个词都对，团队方向是真的，项目是真的，术语用得也准确。**只有把个人实际提交的代码按领域分类，落差才会显形。**
>
> **必须执行** [../../github-audit/references/domain-attribution.md](../../github-audit/references/domain-attribution.md) 的完整核验流程，这在主流程 SKILL.md 中是**第三步半的强制步骤**。仅在本文件读到这条模式而不执行那套流程，等于没查。

**核验方式**：分四栏拆开记录，不要混在一起。**第三栏必须有代码实证，不能靠简历自述填写**：

| 团队背景 | 任务对象 | 个人技术栈（**需代码实证**） | 基础设施责任 |
| --- | --- | --- | --- |
| 在什么方向的团队 | 具体做的是什么东西 | **按 PR 文件路径统计的领域分布，不是简历自称** | 是否真的负责了基础设施 |

**术语掩盖领域**——以下术语听起来是基础设施，但实现可能完全在应用层甚至前端。对每个都要求指出**文件路径**：

| 术语 | 可能的真实实现位置 |
| --- | --- |
| Context Engineering | prompt 拼接逻辑（应用层）vs KV cache 管理（Infra） |
| Middleware Chain | 前端请求拦截器 vs 服务端中间件 |
| Skill / Plugin System | 目录约定 + 前端加载器 vs 真正的沙箱隔离 |
| Agent Runtime / Harness | 一个 while 循环 + 前端状态管理 vs 调度与资源隔离 |
| Memory / 记忆系统 | localStorage / 一个数组 vs 持久化存储层 |

**两个能干净分开应用层与基础设施的追问**：
- "这个上下文压缩，压的是发给模型的 prompt，还是显存里的 KV cache？"
- "Sub-agent 的并发限制，是在前端限制同时发几个请求，还是服务端的资源隔离？"

### 1.9 修正传播不对称

**手法**：最强的主张被广泛传播，而后续的删除、限定或更正只触达少数人。

**核验纪律**：**只有原文与更正都能获取时，才能纳入报告。** 只看到最强版本而未找到更正，不能假定更正不存在。

### 1.10 聚合型模式：多个模块 Owner 并列

**这是一种特殊模式：每条单独为真，但累加起来给读者的印象是假的。**

当简历中连续出现多个模块级 Owner（"A 模块 Owner""B 链路 Owner""C 策略 Owner"），每一条可能都准确——但读者容易把这些局部闭环理解为**整个平台的领导职责**。

**处理方式（重要）**：

> 这一条**不参与逐条计分**，不计入任何单条 claim 的疑点。

它只作为**整体印象提示**和面试切入点存在：建议面试官确认这几个模块之间的关系、各自的团队规模、以及是否存在一个更高层级的负责人。

（此设计是为了不与本文件开头的「规则一：不要重复计分」冲突——聚合印象是独立于逐条判定的另一层观察。）

## 二、指标类主张的核验模式

数字是简历里最容易造假、也最容易识破的部分。

### 2.1 悬浮指标

**识别信号**：给出了精确数字，但缺失以下任意一项：

- **baseline**：从多少降到多少？只说"提升 40%"而不说基数，可能是从 0.1% 到 0.14%；
- **口径**：什么算"成功"？P50 还是 P99？线上还是压测？
- **时间窗**：哪个时间段的统计？大促期间还是日常？
- **归因**：这个提升有多少来自他的改动，多少来自同期的硬件升级、流量变化、其他团队的优化？

**追问方式**：不要问"这个 40% 是怎么算的"（容易被准备过），要问"改动上线前后各观察了多久""有没有做过 A/B 或灰度对比""同期还有别的改动同时上线吗"。

### 2.2 指标的数量级常识检查

有些数字可以直接用工程常识判断合理性：

- 单机 QPS 声称达到某个数量级，但用的技术栈/语言/硬件根本达不到；
- 声称"响应时间从 3s 降到 10ms"——300 倍的提升如果没有换掉整个架构，很难成立；
- 模型准确率提升的数字超过该任务公开 SOTA 的水平；
- 用户量、DAU 与该公司/产品的公开体量矛盾。

命中这类时，**可以给出较强的结论**，因为这是可被独立验证的事实矛盾，而非推测。但仍需在报告中写清推导过程。

### 2.25 单位与口径的硬规则

**规则一：百分点 ≠ 相对变化。** 这是简历里最高频、且可直接判定的一类问题。

> 准确率从 **60% 提升到 70%**，是 **10 个百分点**，相对提升约 **16.67%**。
> 写成"提升 10%"在技术上不算错，但读者会理解成相对提升 10%。

计算方式：
- 相对变化 = `(结果 − 基线) ÷ 基线 × 100%`（100 → 125 是 25%）
- 百分点 = 直接相减（60% → 70% 是 10 个百分点）

**规则二：只在分子、分母、展示值三者同屏时才重算。**

**禁止猜分母。** 看到"转化率 38%"而没有给出分子分母时，**不要推测**——这只能作为面试追问点（"38% 的分母是什么"），不能作为核验结论。

**规则三（最重要的护栏）：重算不一致 ≠ 造假。**

> 数字关系不一致，只说明**在当前给出的口径下**这几个数字对不上。它不自动等于候选人虚假陈述。
>
> 可能存在未披露的分母、不同的统计窗口、或表述省略。**报告中必须写明这一限制。**

比例校验的通过或失败，**仅说明已提供数字之间的关系**，不能单独证明任何事。

**规则四：容差。** 允许约 0.5 个百分点的舍入误差。基线为 0 时判为"无法计算"，不判为矛盾。

**实践提示**：这类重算的**实际触发率很低**——需要分子分母展示值同时出现在简历上才可能触发。不要把它当作主力核验手段。

### 2.27 四类高频指标混淆

| 混淆 | 说明 | 核验方式 |
| --- | --- | --- |
| **系统产出 ≠ 个人产出** | "处理了 2 亿条数据"是系统跑出来的规模，不是个人手工完成的工作量 | 问系统是谁建的、他负责哪一环 |
| **工程指标 ≠ 模型原生能力** | 通过上下文压缩、分段续跑获得的"可持续运行 token 数"，**不等于**基座模型的原生上下文窗口 | 问这个数字是系统能力还是模型参数 |
| **调用量 ≠ 用户数 ≠ 收入** | 接口调用次数不等于独立用户，更不等于付费收入 | 要求明确说"调用"还是"用户" |
| **覆盖率必须给分母与分层** | "覆盖率 85%"要问：分母是什么？按复杂度分桶后各是多少？ | 要求分母定义与复杂度分桶 |

**产品类指标的完整口径清单**（候选人声称用户量、转化率、收入时逐项确认）：
注册用户 / 活跃用户（活跃的定义）/ 付费用户 / 转化事件的定义 / 分母 / 时间窗口 / 收入 / **退款** / **测试与赠送账号是否已剔除** / 用户去重方式。

**第三方流量估算**（如各类站点排名工具的数据）**不能证明**内部支付数据或项目归属。

### 2.3 开源指标的归属混淆

- **Star 数**：项目有 5k star，但候选人只是贡献者之一——Star 不是他的成果；
- **下载量 / 调用量**：项目总量不等于个人贡献带来的增量；
- **"被 XX 公司使用"**：需要区分是项目被使用，还是他的代码被使用。

## 三、技术主张的核验模式

### 3.1 名词堆砌与深度倒挂

**识别信号**：
- 一段 2—3 个月的实习罗列 10 个以上技术名词，横跨多个技术层次（前端 + 后端 + 大数据 + 算法 + 运维）；
- 使用大量当期热点术语（Agent、RAG、MCP、MoE、推理优化、向量检索），但描述停留在这些术语的教科书定义层面，看不出在他的项目里具体解决了什么问题；
- 技术名词之间的组合不合逻辑（如声称用某框架做了它根本不支持的事）。

**追问方式**：挑一个术语，问"你的项目里为什么需要它？不用它会怎样？"——背过定义的人答不出"不用会怎样"。

### 3.2 版本与时间的硬矛盾

这是**唯一可直接归入 `直接矛盾`**的技术核验模式：

- 简历写项目在某时间段用了某技术，但该技术的首次发布时间晚于项目结束时间；
- 声称使用某个已废弃 API 的某个特性，而该特性在声称的版本里并不存在；
- 引用了在声称的时间点尚不存在的模型、框架或规范。

发现这类时可以给出 `直接矛盾` 结论，但必须在报告中给出该技术的公开发布时间及其来源。

### 3.3 架构描述：要产物，不要口才

原先的判据是"能不能说清架构"。**这个判据不够，而且方向反了。**

理由：现代简历包装方法论会专门做一步"技术主线提炼"，帮候选人把整个系统的架构讲得非常清楚。**能把架构讲清楚，恰恰是包装做得好的表现，而不是深度参与的证据。**

正确的分界是：

> **把"候选人实际产出的东西"与"候选人能够解释的系统架构"分开。**
>
> 一个人完全可能准确理解整个项目，却只实现了其中很小一部分。

因此对"架构设计""主导技术选型""核心作者"类 claim，要的**不是口头描述，而是五类产物之一**：

- 本人署名的**设计文档**；
- 对应的 **PR / commit**；
- 本人写的**测试**；
- 本人参与处理的**线上事件 / 故障复盘**；
- 本人主持的**评审记录**。

**说不清架构** → 弱信号（可能只是紧张或表达能力问题，不宜据此下结论）。
**讲得很清楚但拿不出任何产物** → 才是需要在报告中记录的落差。

### 3.35 实现细节密度：精确参数是廉价的可信度装置

**这一条与 §3.3 配套，方向相反但同样重要。**

§3.3 说的是"能讲清架构不等于参与了实现"。这一条说的是更细的一层：**在简历里写出精确的配置参数，也不等于参与了实现。**

**手法形态**：在要点中嵌入高精度的运行时数值与内部链路名，例如：

> 中间件链路 `A → B → C → D → E`；最多 3 并发 / 单任务超时 900s；超 180k 触发轻量压缩，超 250k 触发兜底

**为什么这是一种装置**：
- 这类数值**极易获取**——读一遍配置文件、看一次代码常量、甚至听一次分享就能记住；
- 但它**极难证伪**——外部无法验证某个内部系统的超时是不是 900s；
- 而它在读者那里**极具说服力**——精确数字天然读作"深度参与"的证据。

因此，**细节密度与参与深度之间没有可靠的相关性**。一个只读过代码的人，和一个写了这段代码的人，在简历上可以呈现出完全相同的细节密度。

**正确的核验方式**：不问参数是多少（他知道），问**参数背后的决策过程**：

- "这个超时为什么是 900s 而不是 600s 或 1800s？当初是怎么定下来的？"
- "触发压缩的阈值调过吗？调之前是多少，为什么改？"
- "这个并发上限，是什么资源约束决定的？"

**判断标准**：
- 真正定过这个值的人，能说出**触发原因**——通常是踩过的某个坑（"一开始设 300s，长任务频繁被切断，压测后改的"）；
- 只读过配置的人，会给出**合理但通用**的解释（"根据业务情况权衡的"），说不出具体的调整事件。

**必须排除**：
- 参数确实是别人定的，候选人只是使用者——**这完全正常**，不构成问题，只影响"是否主导设计"这一 claim；
- 时间久远记不清具体调整过程，是合理的；
- 有些参数确实就是拍脑袋定的默认值，没有故事可讲。

**结论上限**：这一条**不能单独得出任何负面结论**。它的用途是**生成追问题**，而不是判定。细节密度高只说明"这条 claim 需要用决策过程而非参数复述来验证"。

### 3.4 技术链路的环节归属核验

**这是一种现有检测会漏掉的包装手法，需要专门识别。**

**手法**：取一个真实的最小闭环，枚举它所"触及"的每一层，用箭头串成一句话：

> 从 0→1 打通 数据清洗 → 结构化标注 → 强化学习训练 → 量化 → 推理服务部署，覆盖数据、训练、强化学习、量化与部署全链路。

**为什么有效**：每个箭头节点在多数组织里对应一个**独立工种**。拼成一条链读起来就是"一个人打通了全栈"。而箭头制造的是**因果与所有权**的观感，比单纯罗列名词强得多。

**为什么现有检测会漏掉它**：§3.1「名词堆砌与深度倒挂」的识别信号是"罗列大量名词、停留在教科书定义层面"。但这类产出的术语**之间有真实逻辑关系**，每个术语在正文中都能找到对应，读起来是结构化叙述而非堆砌。**不要指望名词堆砌检测能命中它。**

**核心核验规则**：

> **链路环节数 ≠ 环节工作量。** 逐环节要产物，且注意各环节的成本极不对称。

| 环节类型 | 最低成本形态（可能只是"用了"） | 应要求的产物 |
| --- | --- | --- |
| **数据** | 跑了一遍别人的清洗脚本 | 去重键定义、有效性判定标准、统计 SQL |
| **训练** | 改了个 yaml 提交任务 | 训练配置 diff、超参、**单变量对照实验** |
| **量化 / 部署** | 调用了一次现成工具链 | 压测报告、服务版本、性能拆解数据 |
| **Agent** | 写了 prompt | 状态机设计、失败恢复策略、异常路径处理 |
| **评测** | 定义了一套分类法 | 样本量、抽样脚本、混淆矩阵、标注一致率 |

**"评测"环节要特别注意**：包装方法论会把**发明一套失败分类法**当作增强表达的手段（如"将失败拆为召回、规划、证据选择、生成四层"）。发明分类法几乎零成本且**不可证伪**。解药是要抽样脚本、混淆矩阵和标注一致性的计算方式。

**追问方式**：不要问"这条链路是怎么设计的"（准备过的人答得很好），要**逐环节问"这一环你具体交付了什么"**。通常只有一到两环能答出细节。

## 四、误伤防范清单

以下情况**绝不能**作为造假的判断依据：

| 现象 | 为什么不是证据 |
| --- | --- |
| 简历写得漂亮、排版专业 | 认真准备简历是求职者应尽的努力 |
| 用了简历模板 / 包装工具 | 工具本身合法，产出内容可以完全属实 |
| 成长速度快、年纪轻职级高 | 存在大量真实的高速成长案例 |
| 学校普通但技术深 | 与能力无关的偏见 |
| 跳槽频繁 / 有职业空窗 | 属于个人选择与际遇，不是诚信问题 |
| 项目是常见类型（如做了个 RAG 应用） | 常见 ≠ 抄袭，见 project-check 的判定标准 |
| 开源贡献是小改动 | 小贡献是正当的开源参与，只有表述夸大才是问题 |
| 私有项目查不到公开痕迹 | 公司内网项目本就不该有公开痕迹 |
| 使用 AI 辅助写代码 / 写简历 | 现代工程实践，与诚信无关 |
| 简历上写了年龄 / 出生年份 | 见下方专条 |

### 关于年龄的硬护栏（不可放宽）

有些简历会把年龄作为亮点前置（"20 岁 · Full-Stack Developer"），或声称"最年轻的 XX"。

**允许做的**：
- 把"最年轻""最早"这类**最高级表述**按 [report-template.md](report-template.md) 的规则归入 `公开检索无支持`——因为它需要一个公开的比较全集才能成立，与年龄本身无关；
- 核验该表述涉及的**可查事实**（如某身份的授予时间是否有公开记录）。

**绝对禁止**：
- **不得用年龄反推经历的可信度**。"这个年纪不可能做到这些"是纯粹的年龄歧视，不是核验；
- **不得用出生日期与某个成就的时间做算术，来推断该成就可疑**。这种推理形式看起来严谨，实际是把受保护属性当作判据；
- **不得因候选人年轻而提高其任何 claim 的举证门槛**，也不得因其年长而降低；
- 年龄、出生年份即使候选人主动写出，也**只作为身份信息**存在，不进入任何推理链条。

**理由**：年龄是受保护属性。一旦允许"从年龄推断合理性"，核验就从"查证据"退化成"凭印象质疑"，而且这种质疑在法律与伦理上都站不住。真正的核验永远指向**证据本身**——某个身份有没有公开记录、某段经历有没有产物——这些与候选人多大年纪完全无关。

**最重要的一条**：如果一个信号有超过一种合理解释，它就只能是"疑似"，且报告中必须写出那个合理解释。
