# 同质化项目特征库

## 这份清单的正确用法（先读这一段）

本文件收录求职简历中高频出现的项目类型。收录**不是**为了给项目贴负面标签。

**做常见项目完全正当**。学一个方向时做该方向的经典项目，是最高效的学习路径；一个技术方向之所以有"经典项目"，正是因为它能有效覆盖该方向的核心知识点。候选人做了个 RAG 应用、秒杀系统或手写 Raft，**这本身是加分项而不是减分项**——它至少说明人动手了。

这份清单只有一个用途：

> **查明该类项目的"典型实现范围"，用来对照简历描述的强度是否超出了这个范围。**

每个条目因此包含三部分：
- **典型实现范围**：跟着主流教程/模板做，通常会做到什么程度；
- **超出范围的标志**：什么样的内容说明候选人做了远超模板的工作（这是**加分信号**，要在报告中如实记录）；
- **需要追问的描述**：哪些简历表述的强度明显超出典型范围，需要面试确认。

**报告纪律**：永远不要写"这是烂大街项目"。要写"该项目属于 XX 类，典型范围是 A/B/C，简历中的 D 超出该范围，建议确认"。

## 一、AI / LLM 方向

### 1.1 RAG 知识库问答

**识别特征**：文档切分 + Embedding + 向量库（FAISS/Chroma/Milvus/PGVector）+ LLM 生成 + 简单前端。目录常含 `loader`/`splitter`/`retriever`/`chain`。多基于 LangChain 或 LlamaIndex。

**典型实现范围**：单路向量召回、固定 chunk size、直接拼接 prompt、无评测体系、无 rerank、单轮问答。

**超出范围的标志（加分）**：多路混合召回（向量 + BM25 + 元数据过滤）、自建 rerank 或使用 cross-encoder、query 改写/意图识别、有可复现的评测集与指标、处理了长文档结构化解析、有 badcase 分析记录、做过 chunk 策略的对比实验。

**需要追问的描述**：
- "自研 RAG 引擎" → 实际是否只是 LangChain 编排？
- "召回准确率提升 40%" → 评测集是什么？谁标注的？baseline 是哪种召回？
- "支持千万级文档" → 向量库实际数据量？有无分片/索引优化？

### 1.2 LLM Agent 框架 / 多智能体系统

**识别特征**：工具调用循环、ReAct/Function Calling、Agent 角色分工、记忆模块。常见目录 `agents/`、`tools/`、`memory/`、`planner/`。

**典型实现范围**：一个 while 循环 + function calling + 几个工具 + 对话历史数组。

**超出范围的标志（加分）**：有失败重试与降级策略、上下文窗口管理与压缩、并发工具调用与依赖编排、可观测性（trace/日志/成本统计）、Agent 效果评测、处理了工具调用幻觉、有沙箱隔离。

**需要追问的描述**：
- "设计 Agent Runtime / 调度内核" → 具体调度了什么？和一个 while 循环的区别在哪？
- "支持多 Agent 协作" → 协作协议是什么？冲突怎么解决？
- "降低 token 成本 XX%" → 怎么统计的？优化手段具体是哪一项起作用？

### 1.3 AI 简历生成器 / AI 面试助手 / AI 客服

**识别特征**：表单输入 + prompt 模板 + 流式输出 + 导出功能。业务逻辑薄，核心是 prompt 工程。

**典型实现范围**：几个 prompt 模板 + API 调用 + 前端渲染。

**超出范围的标志（加分）**：有真实用户与留存数据、做过 prompt 的 A/B 测试、有内容安全过滤、处理了流式中断与重连、成本控制策略。

**需要追问的描述**：主要追问用户量与业务指标的真实来源。

### 1.4 模型微调 / 训练类项目

**识别特征**：LoRA/QLoRA 微调脚本、数据集处理、`transformers` + `peft` + `trl`。

**典型实现范围**：跑通一个开源微调脚本，换自己的数据集，训练一个小模型。

**超出范围的标志（加分）**：自建数据集并说明清洗策略、做过超参对比实验并有记录、有独立评测（非只看 loss）、处理了分布式训练、分析过过拟合/灾难性遗忘。

**需要追问的描述**：
- "模型效果提升 XX%" → 在什么评测集上？和什么 baseline 比？评测集有没有泄漏到训练集？
- "训练了 XX B 参数模型" → 用了什么算力？是全参微调还是 LoRA？

## 二、后端 / 分布式方向

### 2.1 电商秒杀系统

**识别特征**：Redis 预减库存 + 消息队列削峰 + 分布式锁 + 限流。几乎必然出现"超卖"这个词。

**典型实现范围**：Redis 扣减 + MQ 异步下单 + Redisson 锁 + 简单限流。无真实压测或只有本机压测。

**超出范围的标志（加分）**：有完整的压测报告与瓶颈分析、处理了 MQ 消息丢失/重复/顺序、设计了库存最终一致性对账、做过熔断降级演练、分析过热点 key。

**需要追问的描述**：
- "支撑 XX 万 QPS" → 什么硬件？压测工具和场景？是接口层还是下单全链路？
- "解决了超卖问题" → 极端情况下 Redis 与 DB 不一致怎么办？扣减成功但下单失败如何回滚？

### 2.2 手写 RPC 框架

**识别特征**：Netty/Socket + 序列化 + 注册中心（ZK/Nacos）+ 动态代理 + 负载均衡。

**典型实现范围**：能跑通一次远程调用，实现 2—3 种序列化和负载均衡策略。

**超出范围的标志（加分）**：连接池与心跳保活、优雅上下线、超时与重试的幂等处理、异步调用与背压、性能对比数据。

**需要追问的描述**：
- "自研高性能 RPC，性能超过 gRPC" → 怎么测的？测的是什么场景？
- 追问 Netty 的具体细节（见 grill skill）。

### 2.3 手写分布式 KV / Raft 实现

**识别特征**：Leader 选举、日志复制、状态机。常参照 MIT 6.824 / 6.5840 或 raft-java。

**典型实现范围**：完成选举与日志复制，通过课程测试用例。

**超出范围的标志（加分）**：实现了日志压缩/快照、成员变更、线性一致性读（ReadIndex/Lease Read）、做过 Jepsen 类的一致性验证、分析过脑裂与网络分区场景。

**需要追问的描述**：
- "实现了 Raft 一致性协议" → 实现到哪一步？有没有做快照和成员变更？
- "保证强一致性" → 读请求怎么保证？直接读 Leader 本地状态机有什么问题？

### 2.4 微服务电商 / 外卖 / 商城全家桶

**识别特征**：Spring Cloud 全家桶（Nacos/Gateway/OpenFeign/Sentinel/Seata）+ 多个服务模块 + 一套完整业务。代码量大但深度浅。

**典型实现范围**：把技术组件按教程接起来，跑通业务流程。

**超出范围的标志（加分）**：真实的分布式事务方案选型与权衡、服务拆分的边界论证、链路追踪与故障排查实践、真实部署与运维经历。

**需要追问的描述**：
- "设计微服务架构" → 服务边界依据什么划分？为什么不是单体？
- "使用 Seata 保证分布式事务一致性" → 用的哪种模式？AT 模式的全局锁会带来什么问题？

### 2.5 高性能网关 / 短链服务 / IM 系统

**识别特征**：Netty 长连接、协议设计、消息可靠投递（IM）；发号器、缓存、跳转（短链）。

**典型实现范围**：单机跑通核心链路。

**超出范围的标志（加分）**：IM 的离线消息与多端同步、已读回执、消息有序性；网关的插件化与热更新；短链的发号器高可用与防遍历。

## 三、前端 / 全栈方向

### 3.1 仿抖音 / 仿小红书 / 仿知乎

**识别特征**：UI 高度还原某产品，功能覆盖信息流、点赞、评论、关注。

**典型实现范围**：CRUD + 列表渲染 + 简单交互。

**超出范围的标志（加分）**：虚拟列表与无限滚动的性能优化、视频预加载与播放策略、离线缓存、真实的首屏性能数据。

**需要追问的描述**："优化首屏加载 XX%" → 用什么工具测的？优化前后的具体指标项是哪个（FCP/LCP/TTI）？

### 3.2 低代码平台 / 可视化搭建

**识别特征**：拖拽画布 + 组件配置面板 + Schema 渲染 + 出码。

**典型实现范围**：拖拽定位 + JSON Schema + 动态渲染。

**超出范围的标志（加分）**：撤销重做栈、组件通信与数据联动、性能优化（大量组件时）、真实业务落地。

### 3.3 个人博客 / CMS / 管理后台

**识别特征**：Next.js/Nuxt/Hexo + Markdown + 部署。或 React/Vue + Ant Design 的后台模板。

**典型实现范围**：模板套用 + 内容填充。

**需要追问的描述**：这类项目本身难度不高，若简历给了很强的描述（"自研渲染引擎""SSR 架构优化"），需确认具体做了什么。

### 3.4 自研前端框架 / 手写 Vue / React

**识别特征**：实现响应式系统、虚拟 DOM、diff 算法。

**典型实现范围**：跟着源码解析文章实现一个简化版。

**超出范围的标志（加分）**：实现了调度器/时间切片、完整的生命周期、有性能对比、发现并分析了原框架的设计权衡。

## 四、数据 / 算法 / 其他

### 4.1 数据分析看板 / 用户画像

**典型实现范围**：数据清洗 + 几张图表 + 结论。
**需要追问**："通过分析提升 XX 业务指标" → 分析结论有没有真的被采纳？怎么验证的？

### 4.2 量化交易 / 股票预测

**典型实现范围**：拉数据 + 跑几个策略 + 回测。
**需要追问**："年化收益 XX%" → 回测有没有考虑手续费、滑点、幸存者偏差？有没有做样本外测试？是否实盘过？

### 4.3 爬虫 / 数据采集平台

**典型实现范围**：requests/scrapy + 反爬绕过 + 存储。
**需要追问**：主要确认合规性——是否遵守 robots.txt、是否涉及个人信息。这一项的核验重点是**合规意识**而非技术。

### 4.4 竞赛类项目（Kaggle / 天池等）

**典型实现范围**：套用公开 baseline + 调参。
**超出范围的标志（加分）**：有特征工程的独立思考、模型融合策略、公开的排名可核验。
**需要追问**："获得 TOP X%" → 是 public LB 还是 private LB？团队几人？（详见 credential-check）

## 五、跨类别的通用超纲信号（都是加分项）

无论项目属于哪类，出现以下任一项，都说明候选人做了超出模板的真实工作，**应在报告的"可信亮点"一节如实记录**：

- 有 **badcase / 事故复盘**记录，能说清哪里做错过；
- 有**被否决的方案**及否决理由——真实决策必有取舍；
- 有**性能数据的对比实验**，且方法可复现；
- 处理了**异常路径**：超时、重试、幂等、回滚、降级；
- 有**真实用户或真实部署**的痕迹；
- 代码中有针对具体坑的注释（"这里必须加锁，否则 XX 情况下会 YY"）；
- 项目**迭代跨度长**且有明显的演进痕迹。

补充时务必保持本文件的基调：**这是难度基准表，不是黑名单**。
