# GitHub 贡献异常信号库

每条信号标注**权重**与**必须排除的合理解释**。

**使用规则**：
- 单条 `低` 权重信号命中 → 不做任何记录，属于正常波动；
- 多条 `中` 权重信号在同一账号上叠加 → 记为 `疑似`；
- `高` 权重信号 → 仍需排除合理解释后才可记为 `疑似`；只有客观事实矛盾（如 PR 状态、时间戳）才可到 `直接矛盾`。

---

## 一、贡献结构类信号

### A1. 极小改动的广度铺开 —— 权重：中

在 10 个以上不同组织的仓库各提交 1—2 个 PR，且改动均为 T0/T1 级（错别字、格式、链接）。

**为什么是信号**：这种模式的收益函数指向"能在简历上列出的项目数"，而非"对某个项目的实际理解"。深度参与开源的人通常呈现相反形态——集中在 1—3 个项目上，贡献逐步加深。

**必须排除**：
- 候选人是文档/技术写作方向，这就是其专业贡献形态；
- 参加了 Hacktoberfest 等鼓励广泛参与的活动；
- 刚开始接触开源，正在用小 PR 熟悉流程（这是被广泛推荐的入门方式）。

**注意**：命中此信号**不影响对贡献本身的评价**，只影响对"核心贡献者"类表述的核验。

### A2. 明星项目集中 + 改动极小 —— 权重：中

所有 PR 都集中在 star 数最高的知名项目（如主流框架、大厂开源项目），且无一例外都是极小改动。

**为什么是信号**：仓库选择的分布不符合技术兴趣的自然分布，更符合"简历上写出来好看"的选择函数。

**必须排除**：
- 候选人的技术栈本就聚焦于这些主流框架；
- 大项目的 good-first-issue 更完善，新手自然被引导过去。

### A3. 贡献深度无演进 —— 权重：中

时间跨度超过一年，但贡献类型始终停留在 T0/T1，从未出现过 T3 以上。

**为什么是信号**：持续参与一个项目的人，理解会自然加深，贡献类型通常会向上迁移。长期停留在最表层，说明参与是"完成任务式"的。

**必须排除**：
- 该项目对外部贡献者的代码权限门槛很高；
- 候选人的主要精力在工作，开源只是碎片时间的轻度参与——这完全正当。

### A4. PR 描述模板化 —— 权重：低

多个 PR 的标题和正文使用几乎相同的模板措辞，只替换项目名。

**为什么是低权重**：使用模板写 PR 描述本身是效率行为，很多资深贡献者也这么做。仅在与其他信号叠加时才有参考价值。

## 二、时间模式类信号

### B1. 求职季集中爆发 —— 权重：中

全部或绝大部分贡献集中在投递季前 1—3 个月的窗口内，此前账号长期沉寂，此后（如可观察）迅速回落。

**为什么是信号**：贡献动机与求职周期强相关，而非与技术兴趣相关。

**必须排除（重要）**：
- 求职前有意识地积累开源经历，**是完全正当且值得鼓励的行为**。信号本身不代表贡献是假的；
- 学生的空闲时间本就集中在假期，而假期常与招聘季重合；
- 换工作、脱产学习等生活状态变化自然带来活跃度变化。

**正确用法**：不作为负面结论，而是提示"这些贡献可能较新，候选人对项目的理解深度需在面试中验证"。

### B2. 机械化提交节律 —— 权重：高

提交时间呈现精确的机械规律：每天固定时刻、间隔完全均等、或提交内容为无意义的空白/时间戳变更。

**为什么是高权重**：这指向自动化脚本刷绿格子，而非人类工作节律。这是少数可以较有把握判断的模式。

**必须排除**：
- CI 机器人、定时任务、自动化依赖更新（Dependabot 等）产生的提交——这些通常有明确的 bot 标识，**必须先排除 bot 账号的提交**；
- 候选人自己写的自动化工具产生的提交（如自动同步、自动发布），这是正当的工程实践。

**核验方法**：打开这些提交看实际 diff。如果 diff 为空、只改时间戳、或只是无意义的字符增删，信号成立。

### B3. 时间戳与简历矛盾 —— 权重：高（可达 `直接矛盾`）

仓库首次 commit 时间明显晚于简历声称的项目开始时间，或 PR 时间与简历声称的任职期不符。

**为什么可达 `直接矛盾`**：平台侧的 PR/issue/comment 时间戳由 GitHub 生成，无法被用户篡改（commit 的 author date 可篡改，但 push 事件和 PR 创建时间不可）。

**必须排除**：
- 项目从私有仓库/其他平台迁移过来，历史丢失——这很常见，且候选人通常能说明；
- 简历时间写得笼统；
- 使用了 `--amend`、rebase、squash 等操作重写了历史（此时 commit date 会变，但 PR 时间不变，以 PR 时间为准）。

## 三、归属与真实性信号

### C1. 简历表述与 PR 状态不符 —— 权重：高（可达 `直接矛盾`）

简历写"贡献被 XX 项目采用/合并"，而 PR 实际状态为 `open`（未合并）或 `closed`（被拒绝）。

**为什么可达 `直接矛盾`**：PR 状态是客观、公开、无歧义的事实。

**必须排除**：
- 简历撰写时 PR 尚未合并，之后被合并（反向情况也可能）——需比对简历日期；
- 贡献通过其他途径进入（如维护者手动 cherry-pick 后关闭原 PR）——这种情况在 PR 讨论区通常有记录，务必翻看评论。

### C2. fork 仓库被表述为自研 —— 权重：高

简历将一个 fork 自他人项目的仓库描述为"独立开发""从零搭建"。

**必须排除**：
- 基于开源项目做实质性二次开发，且简历中说明了基线——这是正当的；
- 只需检查 fork 之后候选人自己的提交量与改动性质。若在 fork 基础上做了大量实质开发，"独立开发"的说法虽不严谨但情有可原，宜标为"疑似（表述不严谨）"。

### C3. Star 数异常 —— 权重：低

stargazers 中存在大量低活跃度新账号，或 star 曲线有孤立陡峰。

**为什么是低权重**：
- 被技术周刊、热榜、社交媒体转发会造成天然陡峰；
- GitHub 上存在大量真实但低活跃的账号；
- 判断"账号是否真实"本身就不可靠。

**结论上限**：`疑似`，且必须在报告中明确写出"star 数不是可靠的能力指标，本项仅供参考"。

### C4. 代码来源存疑 —— 权重：中

仓库中存在大段与已知开源项目高度雷同、但未标注来源、且许可证信息缺失的代码。

**核验方法**：取特征代码片段搜索比对。发现雷同时，检查：
- 是否是通用样板代码（配置、脚手架生成、框架必需的模板代码）——**这些雷同是必然的，不构成任何问题**；
- 是否保留了原项目的 LICENSE 与版权声明；
- 雷同部分占仓库实质代码的比例。

**必须排除**：
- 脚手架/代码生成器产物；
- 教程项目——照着教程做项目是正当的学习方式，问题只在于简历是否将其表述为原创设计；
- 开源代码在许可范围内的合法复用。

## 三点五、公平性例外：会让真实贡献不可见的四种情况

这四条直接打在"逐个打开 PR 看 diff"这套方法论的盲区上。**核验前必须先排除它们**，否则会把技术很强的人误判成没有贡献：

### F1. 内部贡献被 squash / 镜像 / 服务账号提交

企业内部的开源贡献常常：
- 被 **squash** 成一个 commit，个人的多次提交在历史中消失；
- 通过**镜像仓库**同步到公开侧，作者信息在同步中丢失或统一；
- 由**服务账号 / 机器人账号**统一提交，个人身份完全不出现。

**后果**：一个真正主导了某模块的工程师，在 GitHub 上可能一条记录都没有。

### F2. 名单是示例，不是穷举 —— **名单能证实，不能证伪**

`README` 的"核心贡献者/致谢"列表、官网团队页、甚至部分项目的 `MAINTAINERS` 文件，**常常只是示例或早已陈旧**。

**因此**：
- 名单里**有**候选人 → 是有力的正面证据；
- 名单里**没有**候选人 → **不构成任何反向证据**，不得据此质疑其身份主张。

这是很容易犯且后果严重的错误。

### F3. Maintainer 权限不一定公开

提交权限、review 权限、release 权限的授予在很多项目中不对外公示。查不到权限记录，不能推出没有权限。

### F4. 未合并的 PR 仍是真实工作

关闭或未合并的 PR 依然体现了努力与技术思考，**只是不能证明"已上线的影响"**。区分这两件事：贡献行为为真，落地结果未达成。

### 措辞规范

存在上述任一例外时，报告中使用「**与公开证据存在张力**」，**不使用绝对否定**（如"并非核心贡献者""该身份不属实"）。

## 四、绝不作为信号的观察

以下内容**永远不进入核验**，无论看到什么：

- 候选人 star / follow / watch 了哪些项目或哪些人；
- 提交时间反映的作息（深夜、周末、节假日）；
- profile 中的个人简介、头像、所在地、社交链接；
- 在 issue 讨论中表达的技术观点或与他人的争论；
- 参与的与本岗位无关的项目类型；
- 账号注册时间早晚、粉丝数多少；
- 任何可推断出健康、家庭、政治倾向、宗教信仰的内容。

看到这类信息时主动忽略，不写入任何中间笔记或最终报告。
