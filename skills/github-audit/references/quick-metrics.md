# GitHub 速查量化指标

本文件提供**可在浏览器里几分钟内完成**的量化核验方法，用于在逐个打开 PR 看 diff 之前做粗筛。

数据来源：开源评分项目 [ghfind](https://github.com/hikariming/ghfind) 的确定性打分实现，及其对约 19000 个账号（其中 3444 个深度样本）的实测分布。**该样本偏向自愿参与评分的活跃开发者，分位数整体偏高**——用于判断"这个数字是否异常高"比判断"是否及格"可靠得多。

---

## 零、最重要的校准结论：区分"缺席"与"操纵"

这是本文件最该先读的一段。实测的红旗触发分布：

| 类型 | 红旗 | 触发率 |
| --- | --- | --- |
| **什么都没有** | 空档案（无 bio、粉丝<3、零 star、合并 PR<2） | **10%** |
| **什么都没有** | 无原创作品 | **8.2%** |
| **什么都没有** | fork 堆积（fork 占比 >70% 且非空原创仓库 ≤2） | **7.2%** |
| 主动造假 | 模板化 PR 洪水 | 0.5% |
| 主动造假 | 琐碎 PR 农场 | 0.3% |
| 主动造假 | 关注农场 | 0.1% |
| 主动造假 | 刷 star | **0 次** |

**含义**：主动造假比"账号是空的"少一到两个数量级。

因此 `github-audit` 的输出**必须把结论分成两类**，绝不能混为一谈：

- **「公开足迹薄」**——中性事实。绝大多数工程师的代码在公司内网、私有仓库、公司自建 GitLab。这**不是任何负面信号**，只说明"这个维度无法提供证据"，应转为面试问题。
- **「存在操纵痕迹」**——需要多条信号叠加才能成立，且极为罕见。

把前者写成后者，是这个维度最容易犯、后果最严重的错误。

## 一、检测模式，不检测事件

第二条关键校准：

> **58% 的开发者至少有一个琐碎的外部 PR（完全正常）。只有 0.4% 的人是"多数 PR 都琐碎"。**

任何惩罚"提过小 PR"这个**事件**的规则，都是为了抓 11 个人而误伤 1486 个人。

**对 T0–T5 分级的直接约束**：单个 T0 PR 不构成任何信号。报告里不要写"该 PR 为 T0 级"，要写"**N 个外部 PR 中，T0/T1 占比 X%**"。造假是账号历史的**比例属性**，不是单个 diff 的**事件属性**。

---

## 二、第一分叉：外部仓库 vs 自有仓库

**在统计任何 PR 指标之前，先按目标仓库的 owner 分叉。** 这是所有 PR 信号的前置步骤。

| 类型 | 判定 | 意义 |
| --- | --- | --- |
| 打向**自己**仓库的 PR | owner == 候选人 | **不算刷量**（solo dev 的正常工作流），但也**不算生态影响力** |
| 打向**外部**仓库的 PR | owner != 候选人 | 这才是可核验的开源贡献 |

**速查**：打开 `https://github.com/pulls?q=is:pr+author:{用户名}+is:merged`，列表右侧直接显示每个 PR 的目标仓库。

**核验用法**：简历写"N 个开源贡献"时，**剔除自有仓库后再数一遍**。如果数量掉去 80%，这是需要在报告中说明的重大落差。

## 三、PR 内容的机械分类（3 秒/个）

打开 PR 的 **Files changed** 标签页，看文件路径和后缀。这是把 T 分级从主观判断变成半客观判定的前置步骤：

| 类别 | 判定规则 |
| --- | --- |
| **文档类** | 后缀 `.md .mdx .rst .adoc .txt`；或路径含 `docs/ site/ website/ blog/ content/ examples/ templates/ tutorials/ guides/ i18n/ locales/`；或文件名为 `README CHANGELOG CONTRIBUTING LICENSE` |
| **表现层类** | 后缀 `.css .scss .less .svg .png .jpg .gif .webp`；或路径含 `assets/ public/ demo/ storybook/ screenshots/ __snapshots__/` |
| **核心代码类** | 后缀 `.c .cc .cpp .cs .go .java .js .jsx .kt .php .py .rb .rs .scala .swift .ts .tsx` 且不落在上述两类路径中 |

**PR 级判定式**：
> 文档文件 > 0 **且**（核心代码文件 = 0 **或** 文档文件占比 ≥ 60%）→ 判为**文档类 PR**

**琐碎（trivial）判定**：Files changed 页顶部的 `+N −M`，**additions + deletions ≤ 5 行**。

**建议把 T 分级拆成两个正交轴**：**类型轴**（文档 / 表现层 / 核心代码）×**深度轴**（T0–T5）。把"改 README 里的架构说明"和"改架构代码"放在同一个梯子上会失真。

⚠️ **不要用仓库名的正则去猜类型**。名字里带 `templates`/`examples`/`algorithm` 的完全可能是真代码库（模板引擎、算法库）。仓库名只能作为"提示人工复查"，不能作为判据。

## 四、star 含金量三件套（30 秒）

打开候选人 star 最多的那个仓库主页，看顶部三个数字：

| 指标 | 计算 | 判读 |
| --- | --- | --- |
| **fork / 100 star** | `forks ÷ (stars/100)` | < 1.0 且几乎无 open issue → 值得复查，但见下方警告 |
| **社区互动率** | `(watchers + 历史 issue 总数 + 历史 PR 总数) ÷ stars` | **≥4% 正常**；2–4% 偏低；1–2% 较低；**<1% 明显偏低** |

**实证锚点**：病毒式传播的清单/资源合集类仓库互动率普遍 <1%（例：5.7k star 仅 18 个 issue、2 个贡献者 = 0.97%）；而重量级旗舰项目普遍 ≥5%。

**适用门槛与免责（重要）**：
- 仓库需 **≥500 star** 才有统计意义；
- **mirror 仓库、关闭了 issue 功能的仓库不适用**，直接跳过；
- 互动率低的最常见原因**不是刷 star，而是项目类型**——资源合集、awesome 列表、教程仓库天然互动率低，这完全正常；
- 前述实测中**刷 star 检测的触发率为 0**，说明这个信号在真实场景中极少成立。**结论上限为"该项目的互动率偏低，star 数不宜作为技术能力指标"**，不要推向"疑似刷 star"。

## 五、模板化 PR 洪水（60 秒）

这是实测数据支撑最强的信号——分布呈**双峰**，中间几乎没有过渡带。

**速查法**：打开 `https://github.com/pulls?q=is:pr+author:{用户名}`（默认按创建时间倒序），看最近 30 条：

1. **单仓集中度** = 打向同一仓库的条数 ÷ 30 → **≥50% 且该仓库不属于本人**
2. **标题模板率** = 把标题小写去空格后取**前 18 个字符**当 key 分组，最大组条数 ÷ 30
3. **两条同时命中**才算可疑

**标题模板率的实测分布**：

| 分位 | p25 | p50 | p75 | p90 | p99 |
| --- | --- | --- | --- | --- | --- |
| 模板率 | 0.07 | **0.07** | 0.13 | 0.20 | 0.72 |

中位数 7%，而被标记账号普遍 >50%——**双峰、无中间地带**，所以这个指标的判读相对干净。

**必须遵守的纪律**：
> **标题模板化和仓库集中度本身只是模式风险，不是低质量的证明。** 给出较强结论必须有旁证——文档类占比高 / 维护者拒绝率高 / 核心代码 PR 少 / 自有项目薄弱，四者中至少满足两条。
>
> 一条一行的 PR 完全正常；一百条打向同一个仓库、标题几乎相同，才不正常。

## 六、百分位对照表

用于回答"这个数字到底算不算突出"。**样本偏向活跃开源开发者，分位数整体偏高**。

| 指标 | p25 | **p50（中位）** | p75 | p90 | p99 |
| --- | --- | --- | --- | --- | --- |
| followers | 3 | **27** | 205 | 1,275 | 19,073 |
| 总 star | 2 | **34** | 624 | 5,876 | 100,284 |
| 单仓最高 star | 1 | **16** | 337 | 3,231 | 73,027 |
| 合并 PR 总数 | 1 | **20** | 152 | 598 | 3,260 |
| 账号年龄（年） | 4.4 | **7.4** | 11.0 | 14.1 | 17.9 |
| 去年贡献数 | 27 | **291** | 1,139 | 2,705 | 9,645 |
| 公开仓库数 | 10 | **28** | 66 | 132 | 421 |
| 创建的 issue 数 | 1 | **14** | 73 | 236 | 1,630 |
| 维护者拒绝率 | 0 | **0.02** | 0.06 | 0.13 | 0.35 |

**用法**：候选人有 500 followers 时，这大约是 p80——值得记为亮点，但不是"顶尖"。有 5000 star 的项目大约是 p90，这确实突出。

**⚠️ 不要反过来用**。低于中位数**不构成任何负面信号**——中位数意味着一半的真实开发者都在下面，且样本本身偏向活跃开源者，普通工程师的真实分布还要更低。

## 七、PR 接受率：一个没有区分度的指标

**实测：维护者拒绝率的中位数只有 2%，p90 才 13%。**

> 结论：只要一个人有合并过的 PR，他提的东西基本都会被合。**"PR 接受率高"是所有人的默认状态，不构成亮点，不要给它加分。**

只有 **>50%** 这种极端值才有信息量。

**且必须正确计算拒绝率**——不是所有 closed-unmerged 都是被拒：

| closer 是谁 | 在谁的仓库 | 是否算拒绝 |
| --- | --- | --- |
| 作者本人 | 外部仓库 | **不算**（rebase、base 分支搞错、上游方向变了、重复提交，都会导致作者自关） |
| 作者本人 | 自己仓库 | 不算 |
| 其他人 | 外部仓库 | **算拒绝** |

速查：`is:pr+author:{用户名}+is:closed+is:unmerged`，打开几条看是谁点的 Close。

## 八、项目实质性 checklist（1 分钟/仓库）

用于判断一个仓库是真项目还是 README 空壳。逐项打勾累加：

- [ ] **代码量**：仓库 size ≥1000KB `+0.25` / ≥200KB `+0.2` / ≥50KB `+0.15` / ≥10KB `+0.08` / **= 0 → 直接判 0，一票否决**
- [ ] 有主语言标注 `+0.15`
- [ ] 仓库描述 ≥20 字符 `+0.15`
- [ ] README ≥800 字符 `+0.25` / ≥300 `+0.2` / ≥120 `+0.12`
- [ ] README 含 install / usage / api / demo / features / deploy / test / architecture / screenshot 任一章节 `+0.1`
- [ ] 最后 push 距今 ≤180 天 `+0.1` / ≤365 天 `+0.07` / ≤730 天 `+0.04`

**判读**：≥0.6 是像样的项目，<0.3 基本是空壳。

**占位项目降权**：仓库名或描述含 `wip todo tmp temp scratch playground practice learning notes leetcode algorithm blog profile`，或仓库名等于用户名（profile README 仓库）→ 总分 **×0.25**（README ≥600 字符且 size ≥200KB 时 ×0.55）。

⚠️ 这个关键词表**误伤率高**——一个叫 `xxx-algorithm` 的真算法库、一个认真写的技术 blog 引擎都会被命中。**只用作"提示复查"，不作为判据。**

⚠️ 更重要的是：**空壳仓库不等于造假**。个人练习仓库、学习笔记仓库是绝大多数人 GitHub 的正常构成。这个 checklist 只在**简历把某个仓库作为核心项目展示**时才适用——核验的是"简历描述与仓库实际内容的落差"，不是"这个人的仓库质量"。

## 九、维护者身份的硬证据（最快、最难伪造）

核验简历里的"核心贡献者 / Maintainer / 核心作者"时，**先查这两项**：

| 证据 | 强度 | 怎么查 |
| --- | --- | --- |
| **出现在 `MAINTAINERS` / `CODEOWNERS` / `OWNERS` 文件** | **最硬** | 仓库根目录搜文件 |
| **是某个 release / tag 的发布者** | **最硬** | 仓库 Releases 页看发布者 |
| 是该 org 的公开成员 | 中 | `/orgs/{org}/people` |
| 长期强贡献 | 中 | Insights → Contributors，看 commit 数与跨年度分布 |
| 用户 pin 了该仓库 | 弱 | 个人主页 |

"长期强贡献"的量化参考：≥2 年活跃且 ≥50 commit；或 ≥2 年且 ≥20 commit + ≥10 PR；或单年 ≥100 commit。

⚠️ **反向不成立**：不在 `MAINTAINERS` 名单里**不能**作为反证——很多项目不维护公开名单，名单可能陈旧，README 的"致谢/核心贡献者"列表常常只是示例而非穷举。**名单能证实，不能证伪。**

## 十、蹭明星项目的核验（防"我贡献过 pytorch"）

简历声称贡献过某知名项目时：

打开 `https://github.com/{org}/{repo}/commits?author={用户名}`，数 commit 数。

| commit 数 | 结论表述 |
| --- | --- |
| < 3 | 按"**接触过 / 提交过个别改动**"记，不能表述为"贡献者" |
| ≥10 commit 或 ≥3 个合并 PR | 可算**实质参与** |

**外部仓库 ≥200 star 才算"有影响力的贡献目标"；自有仓库需 ≥1000 star。fork 仓库一律不算**——fork 的 star 是借来的。

## 十一、这套指标不能做什么

1. **不生成总分。** 评分体系是为公开排行榜设计的，含有对新账号、对企业内网工作者的结构性惩罚。招聘核验需要的是"简历表述 vs 可核验证据"的落差清单，不是一个把异质信号压成一个数、让人无从追溯的分数。
2. **不惩罚低活跃度、不惩罚 fork 工作流、不惩罚新账号。** 转行两年的优秀工程师，公开足迹天然少于注册十年的平庸账号。fork → 改 → PR 本身就是标准的贡献工作流。
3. **不用于筛选，只用于分流。** 这些指标的用途是决定"哪几个 PR 值得打开细看"，而不是给候选人定性。
4. **每条量化结论仍须写出"另一种可能"。** 阈值不改变本技能包的基本纪律——数字让判断更快，不让判断更硬。
