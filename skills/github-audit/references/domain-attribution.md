# 代码领域归属核验

## 为什么必须单独有这一维

本技能包原有的 PR 分类（`文档类 / 表现层类 / 核心代码类` × `T0–T5` 深度）测的是**贡献的分量**，完全测不出**贡献的领域**。

这留下了一个可以直接击穿整套核验的漏洞：

> 一个人在 AI Infra 项目里写 100% 前端 TypeScript，按原分类会被判为「**核心代码类 · T5 特性/架构级**」——最高档。
> 与此同时，简历写「AI Infra 工程师，负责 Agent Runtime 与 Context Engineering」。
> **原有的每一条规则都会通过，因为没有任何一维在看"这些代码属于哪个方向"。**

**核心原则**：

> **项目的领域标签 ≠ 个人的工种。**
> 在一个 AI 项目里写前端，仍然是前端工作。在一个数据库项目里写文档站，仍然是文档工作。

这不是贬低——前端是完全正当且有价值的工程方向。**问题只在于简历用项目的方向标签覆盖了个人的实际工种。**

---

## 一、这一步是强制的，不是可选的

**触发条件**：只要简历中出现**方向性自称**，就必须执行本核验。方向性自称包括：

- 岗位定位："AI Infra 工程师""分布式存储方向""推理优化""基础架构"
- 项目角色："Agent Runtime Owner""调度模块核心作者""训练链路负责人"
- 技能栏的方向声明

**不执行本核验就出报告 = 核验未完成。** 报告中必须显式写出本维度的结论，即使结论是"无法判定"。

---

## 二、领域分类表（按文件路径与后缀机械判定）

打开 PR 的 **Files changed**，按下表给每个文件归类。**先看路径，再看后缀**——路径比后缀更可靠。

| 领域 | 典型路径 | 典型后缀 |
| --- | --- | --- |
| **前端 / 客户端** | `web/ frontend/ ui/ client/ components/ pages/ app/ views/ styles/ public/ src/app/` | `.tsx .jsx .vue .svelte .css .scss .less .html` |
| **后端 / 服务** | `server/ api/ service/ handler/ controller/ router/ middleware/`（**注意**：`middleware/` 在前端项目里也常见，看上下文） | `.go .java .rs .php .rb` + 服务上下文中的 `.py .ts` |
| **基础设施 / 平台** | `infra/ deploy/ ops/ k8s/ helm/ terraform/ ansible/ .github/workflows/ docker/` | `Dockerfile .tf .yaml(部署类) .sh` |
| **ML / 训练** | `train/ training/ finetune/ sft/ rlhf/ model/ dataset/ eval/` | `.py` 且 import `torch/transformers/peft/trl/deepspeed` |
| **推理 / Serving** | `serving/ inference/ engine/ scheduler/ kernel/ runtime/ worker/` | `.cu .cpp` + 推理上下文中的 `.py` |
| **数据 / 管线** | `etl/ pipeline/ ingestion/ warehouse/ dbt/` | `.sql` + 数据上下文中的 `.py .scala` |
| **存储 / 内核** | `storage/ engine/ txn/ wal/ index/ buffer/ replication/` | `.c .cpp .rs .go` |

### 三条判定纪律

**1. 语言不决定领域。** `.py` 可能是训练脚本、可能是 Web 后端、可能是构建工具。`.ts` 可能是前端、可能是 Node 服务、可能是 CLI。**必须看路径和实际改动内容。**

**2. 拿不准就标"无法判定"，不要猜。** 一个 monorepo 里 `src/core/` 可能是任何东西。打开文件看几行比猜可靠。

**3. 按行数加权，不按文件数。** 改了 1 行后端配置 + 500 行前端组件，领域归属是前端。报告里给的应是**改动行数的领域分布**。

## 三、输出：领域分布 vs 方向自称

核验的产出是一张对照表：

```markdown
### 代码领域归属

**简历的方向自称**：[原文摘录，如"AI Infra 工程师，负责 XX Runtime"]

**实际代码的领域分布**（基于 N 个 PR，共 M 行改动）：
| 领域 | 行数占比 | 代表 PR |
| 前端/客户端 | 78% | [链接]（改动：组件、样式、页面路由） |
| 后端/服务 | 12% | [链接] |
| 基础设施 | 6% | [链接] |
| 推理/Serving | 0% | — |
| ML/训练 | 0% | — |
| 无法判定 | 4% | [链接] |

**对照结论**：[见下方判定表]
```

### 判定表

| 方向自称 | 代码实证 | 结论 | 说明 |
| --- | --- | --- | --- |
| AI Infra / 推理 / 训练 | 该领域占比 **≥50%** | `已核实` | 自称与实证吻合 |
| AI Infra / 推理 / 训练 | 该领域 **10–50%** | `部分属实` | 确有该方向工作，但不是主体；需说明个人边界 |
| AI Infra / 推理 / 训练 | 该领域 **<10%**，主体在其他领域 | `部分属实（强）` 或 `直接矛盾` | 见下方"定档说明" |
| 任何方向 | 公开代码不足以判定 | `待核验` 或 `结构性不可公开核验` | **不得推向负面** |

### 定档说明（重要）

**什么时候可以到 `直接矛盾`**：
- 简历明确声称**个人负责/主导**某个技术方向的实现（如"Agent 调度内核 Owner""推理引擎核心作者"）；
- 而该项目**全部可见的个人提交**都在另一个领域（如全部是前端组件与样式）；
- 且已排除下方全部公平性例外。

此时"个人主导了 X 方向的实现"与"个人的全部可见产出都在 Y 方向"构成互斥事实，可摘录、可复现。

**什么时候只能到 `部分属实`**：
- 简历用的是团队/项目层面的描述（"在 AI Infra 团队""参与 XX 项目"）而非个人实现主张——**这类表述本身没错**，团队背景就是团队背景；
- 或该方向有少量真实提交，只是不构成主体。

## 四、必须排除的公平性例外（缺一不可）

**这一维的误伤后果很重，以下每条都必须先排除**：

### E1. 领域工作可能不在这个仓库

一个人在公司内部做推理优化，同时在公开仓库维护前端——**两件事都是真的**。公开仓库的领域分布**不能代表其全部工作**。

**处理**：若简历声称的方向工作发生在**公司内部系统**，本维度结论为 `结构性不可公开核验`，**不得据公开仓库的领域分布做负面判断**。只有当简历把**该公开项目本身**作为方向证据时，本核验才适用。

### E2. squash / 镜像 / 服务账号

见 [contribution-red-flags.md](contribution-red-flags.md) F1。内部贡献可能完全不可见或归属错误。

### E3. 设计与实现可以分离

有人负责方案设计、技术选型、评审，实现由他人完成。**这是完全正常的分工**，尤其在资深角色上。

**处理**：此时要的是设计产物（RFC、设计文档、评审记录），而不是代码行数。**不得因"没写这部分代码"就否定其方向参与**。

#### 怎么在公开材料里区分"设计者"与"使用者"

E3 常被当成万能挡箭牌——"代码不是我写的，但方案是我定的"无法证伪。其实公开侧有一个很有效的抓手：

> **看 PR / issue 里的讨论记录，而不是代码行数。**

**设计者会留下方案争论**：为什么选 A 不选 B、某个边界情况怎么处理、被 reviewer 质疑后如何回应、主动指出自己方案的代价。**使用者不会**——他们的评论集中在"怎么用""报错了""能不能加个参数"。

具体去看：
- 该模块相关 issue 里，候选人有没有发起过**设计讨论**（而非只提 bug）；
- PR 的 review 往返中，他是**被质疑的一方**还是**质疑别人的一方**；
- 有没有 RFC / design doc 类的文档提交，或在 issue 里写过较长的方案对比；
- 是否参与过**别人 PR 的 review**——评审他人代码是设计话语权最直接的证据。

**这一条同样适用于反向保护**：若候选人在讨论区留下了实质的方案论证，即使代码行数不多，"参与设计"也应被采信。

### E4. 全栈与跨领域是常态

很多工程师本来就跨领域工作。前端占比高**不代表**不懂后端。

**处理**：本核验判定的是"**简历的方向自称是否被代码实证支持**"，不是"这个人会不会某个方向"。

### E5. 领域边界本身是模糊的

Agent 系统的 prompt 编排、工具注册、上下文管理——**它们到底算不算 Infra，业界没有统一答案**。

**处理**：遇到边界模糊的模块，标为"无法判定"并在报告中说明分歧，**不要强行归类到对候选人不利的一侧**。

### E6. 前端不低人一等

**必须在报告中显式声明**：本维度**不评价任何领域的价值高低**。前端、文档、测试都是正当且必要的工程方向。核验的是**表述与实证的一致性**，不是工种的贵贱。

## 五、术语掩盖领域

**这是最需要警惕的一层。** 有些术语听起来是 Infra，但实现可能完全在应用层甚至前端：

| 术语 | 可能的实现位置 | 核验方式 |
| --- | --- | --- |
| Context Engineering | 可能是 prompt 拼接逻辑，也可能是 KV cache 管理 | 问：改的是哪一层？有没有碰到显存/序列化？ |
| Middleware Chain | 可能是前端请求拦截器，也可能是服务端中间件 | 看文件路径 |
| Skill / Plugin System | 可能是目录约定 + 前端加载器 | 问：注册、隔离、沙箱各在哪实现？ |
| Agent Runtime / Harness | 可能是一个 while 循环 + 前端状态管理 | 问：调度、并发、资源限制在哪一层？ |
| Memory / 记忆系统 | 可能是 localStorage / 一个数组 | 问：持久化在哪？跨会话怎么做？ |
| Scheduler / 调度 | 可能是任务队列 UI | 看是否碰到线程/进程/显存 |

**核验动作**：对每个 Infra 味道的术语，**要求指出对应的文件路径**。答不出具体路径，或路径全在 `web/`、`components/` 下，就是领域落差。

---

## 六、把它变成面试题

领域落差最好的验证方式是让候选人自己定位：

> "你提到的 [Infra 术语]，我想看看具体实现——它在仓库的哪个目录下？主要是哪几个文件？"

**判断**：
- 真在那一层工作过的人，能直接说出路径，且路径与领域吻合；
- 若答出的路径全在前端目录，而简历表述是 Infra，**落差当场确认，且是候选人自己说出来的**——这比核验者的推断可靠得多。

**追问**（针对具体术语）：
- "这个上下文压缩，压的是发给模型的 prompt，还是显存里的 KV cache？"
- "Sub-agent 的并发限制，是在前端限制同时发几个请求，还是在服务端做的资源隔离？"

这两问能干净地把**应用层编排**与**基础设施**分开——而这正是"AI Infra"自称最常见的落差所在。
