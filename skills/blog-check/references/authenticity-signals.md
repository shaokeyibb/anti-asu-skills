# 技术内容真实性信号

本文件用于判断一篇技术文章的**内容来源**与**实践含量**。

**总原则**：技术写作的相似性是天然的、大量的、不可避免的。讲同一个 API、同一个算法、同一份官方文档，写出来必然像。因此本文件中**没有任何一条单独信号可以支撑抄袭结论**。

---

## 一、搬运与抄袭

### S1. 整段正文逐字命中更早的公开内容 —— 权重：**最高，且这是首选方法**

**直接搜整段正文，不要去挑"特征句"。**

#### 为什么整段搜远优于挑特征句

1. **组合唯一性**：一段 100—300 字的连续文字，即使**每一句单独看都很通用**，组合起来仍然是唯一指纹。两个人独立写出逐字相同的一整段，概率趋近于零。
2. **绕开了最脆弱的一环**：挑特征句要求核验者判断"这句够不够独特"——**而这个判断正是整套流程最容易失败的地方**。技术讲解段落逐句看全是通用表述，核验者会判定"没有特征句可用"而跳过，于是整段搬运的内容被漏掉。
3. **成本更低**：一篇文章一次检索即可，不需要先通读找出"最独特的那句"。

> **教训**：不要因为一段文字"看起来很通用"就跳过它。**通用的句子组成的长段落，依然是指纹。**

#### 操作方法

1. **选段**：取文章**中部的一个解释性段落**，100—300 字。
   - 避开开头和结尾（导语、总结句式化程度高，本就容易雷同）；
   - 避开纯代码块（代码雷同是正常的）；
   - **包含代码的段落取其文字说明部分**。
2. **加引号精确检索**该段（或前 2—3 句，若搜索引擎对长串支持不佳）。
3. **对每一篇抽样文章都做一次**——这一步很便宜，不要只对"可疑的"做。
4. 命中后，**追溯到最早/权威出处**，而不是停在任意一个命中结果上（内容农场会大量回声，见下）。

#### 判定

- **整段逐字命中 + 命中源发布更早 + 该源是公认出处** → 强证据，进入下方四要件排除流程；
- **多篇文章都整段命中同一来源** → 指向**系统性**，应在报告中给出**命中率**（"抽样 N 篇，M 篇整段命中，命中率 X%"），而非笼统定性。

**必须排除（缺一不可）**：
- **同人多平台**：同一作者把文章同步发到个人博客、掘金、知乎、CSDN、公众号——**这是最常见的情况**，且完全正当。核验作者名、头像、简介、互链关系。
- **标注了转载/参考**：文章开头或结尾有原文链接、"转载自"、参考文献列表。
- **反向抄袭**：候选人是原作者，别人抄了他的。看首发时间。
- **共同来源**：两篇文章都参考了同一份官方文档或经典教程，导致雷同。**注意**：共同参考会导致**结构与结论**相似，但**不会导致整段逐字相同**。整段逐字命中时，这条解释通常不成立。
- **平台自动同步/镜像站**：大量内容农场会自动抓取转载，命中它们没有意义。

#### 内容农场回声的处理（整段搜必然遇到）

整段检索常会返回几十个逐字相同的结果——**这不代表"到处都是所以无从判断"**，恰恰相反，它证明这段文字是被大量复制的内容。

**追溯步骤**：
1. 按发布时间排序，找**最早**的那个；
2. 识别**权威出处**——有作者署名、有完整体系（成书/成专栏）、被他人引用的那个，通常就是源头；
3. 排除掉无署名、内容拼凑、站点本身就是聚合器的结果；
4. **比对候选人的发布时间与源头**。

**关键**：若源头明确且早于候选人，"网上到处都有"**不能**作为候选人的辩护——那些回声站点同样是转载方。

**结论上限**：四项排除全部完成且雷同度极高、无任何来源标注时，可标 `部分属实`。**不给 `直接矛盾`**——因为你无法完全排除线下授权、代笔约定等你看不到的情况。

### S1.5 标题逐字命中已知来源 —— 权重：高，且**可全量筛查**

**这是搬运最强、也最廉价可查的痕迹。**

转述者通常**保留原标题**——因为标题是原作者拟好的、最吸引点击的问句式表达，改了反而流量下降。因此标题往往比正文更早暴露来源。

**方法**：拉取全量标题列表，与下方"高频被转述来源"的章节目录逐字比对，统计**命中数 / 总数**。这一步不需要读正文，**几分钟就能给出全量结论**，且可复现、可追溯。

**高频被转述来源**（中文技术圈，按被转述频率）：

| 来源 | 典型标题形态 |
| --- | --- |
| 小林coding（xiaolincoding.com）《图解网络》《图解系统》《图解MySQL》 | 问句式："用了 TCP，数据就一定不会丢失吗？""执行一条 select 语句，期间发生了什么？""MySQL 一行记录是怎么存储的？" |
| JavaGuide | "XX 面试题总结""XX 详解" |
| 代码随想录 | 算法题解，按题号成篇 |
| labuladong 算法笔记 | "XX 算法框架""如何XX" |
| 阿秀的学习笔记 / CS-Notes / 面试宝典类 | 八股整理 |
| 极客时间专栏、掘金高赞长文 | 系列连载 |

**判定**：标题逐字相同 + 发布更晚 + 该来源是公认更早出处 → 进入 S1 的四要件排除流程。

**必须排除**：
- 通用技术标题的天然重合（"什么是 TCP 三次握手""B+树详解"）——**这类不能算命中**，只有**独特句式**（问句、反问、"其间发生了什么"这类修辞）才算；
- 同人多平台分发；
- 明确标注了转载。

### S1.6 部分标注：**加重情节，不是减轻情节**

这是一个极易犯的推理错误，单独列出。

**场景**：同一批同源文章中，有一篇标了"摘自 XX"或残留了原站链接，其余若干篇未标注、且被标记为"原创"。

**错误的推理**（务必避免）：
> ~~"作者有标注习惯，说明并非有意隐瞒，属于标注时有时无的疏忽" → 减轻~~

**正确的推理**：
> 那一篇标注**证明作者知道这批内容是转述的**。既然知道，其余同源文章被标为"原创"就**不能用"不知道"来解释**。
>
> 部分标注 → **加重**，不是减轻。

同理，正文里残留的"我在上一篇文章……"（而"上一篇"指向原站的上一章）**是整段搬运未清理的直接痕迹**，属于强证据，不是瑕疵。

**仍需保留的合理解释**（写进报告，但不改变上述方向）：
- 平台的"原创/转载"是**默认勾选项**，批量发布时不改默认值确实常见；
- 作者可能主观上把"读完 + 自己跑一遍 + 重新组织"视为原创；
- 若文章中**确有作者自己的实验输出、报错记录、代码**，则属"在他人框架上加入了自有内容"，与纯粘贴不同，应如实区分。

**但这些解释影响的是"性质"（是疏忽还是有意），不影响"事实"（这些内容不是原创）。** 报告应分开写这两层。

### S2. 文内风格断层 —— 权重：中

同一篇文章中：人称突变（"笔者"与"我"混用）、术语翻译不一致（同一概念前后用不同译名）、代码风格不统一、繁简混杂、深度骤变（前半部分泛泛而谈，中间突然出现极深的细节，之后又回到浅层）。

**必须排除**：多次修订、引用了他人代码块、翻译整合多份材料、写作跨度长。

### S3. 上下文断裂 —— 权重：中

文章提到"上一篇我们讲过 X"，但博客里根本没有那一篇；引用了"如图所示"但没有图；提到"我们项目里"但整个博客从未提过任何项目。

**为什么是信号**：这是从他处复制片段时最容易留下的痕迹——原文的上下文没跟过来。

**必须排除**：文章迁移时丢失了图片、系列文章删除了部分、跨平台搬运自己的旧文时未同步。

## 二、内容空洞（不是抄袭，是另一个问题）

**重申**：这一节判断的是**内容有没有实践含量**，绝不是判断"用没用 AI 写"。AI 辅助写作是正当且普遍的实践，**任何情况下都不得输出"这是 AI 生成的"这类结论**。AI 检测在原理上不可靠，误判率高到不可用于任何有后果的判断。

正确的表述始终是对内容的描述：**"该文以概念复述为主，未见具体工程实践细节"**。

### E1. 结构完美但信息密度低 —— 权重：中

- 小标题极度工整对称，每节篇幅几乎相同；
- 大量"首先/其次/再者/此外/最后/总而言之"这类纯连接词占位；
- 每段都以概括句开头、总结句结尾，但中间没有具体信息；
- 通篇没有一个具体的版本号、报错信息、数值、配置项。

### E2. 与权威来源信息量等同 —— 权重：中

把文章内容与该技术的官方文档对照，如果**没有任何增量信息**（没有官方文档没提的坑、没有实际使用中的发现、没有对比、没有场景化建议），那么这篇文章对评估技术深度没有参考价值。

**这不是负面结论**，只是"该样本无法提供深度证据"。

### E3. 代码示例未经运行 —— 权重：中

代码有明显语法错误、调用了不存在的 API、参数与该版本不符、输出结果与代码逻辑不符。

**必须排除**：版本演进导致 API 变化（老文章的代码在新版本下不能跑是正常的）、伪代码、示意性片段、编辑器/平台的格式破坏。

### E4. 只有 happy path —— 权重：低

从不提失败、从不提边界、从不提"这个方案的代价是什么"。

**必须排除**：入门教程本就应该聚焦主流程，这是好的写作选择而非缺陷。

## 三、真实实践的正向信号（务必记录为加分）

发现以下任一项，说明文章背后有真实的工程实践，**必须在报告的"可信亮点"中记录**：

| 信号 | 为什么难以伪造 |
| --- | --- |
| 完整的报错信息 + 排查路径 | 具体的报错栈是环境特定的，编不出来 |
| "我一开始以为是 A，查了半天发现是 B" | 认知修正的过程反映真实的思考轨迹 |
| 精确的版本号与环境组合 | 只有真跑过才知道是哪个版本组合出的问题 |
| 官方文档没写清楚的补充说明 | 需要真的踩过才知道文档哪里不够 |
| 明确的适用边界（"这招在 XX 场景下不行"） | 需要在多个场景验证过 |
| 有数据的对比实验（含实验方法） | 需要真的做过测试 |
| 评论区的实质技术讨论与作者回复 | 需要真懂才答得上追问 |
| 后续勘误 / 更新说明 | 说明作者持续在用这个技术 |
| 讲了一个失败的尝试及原因 | 编造的内容通常只讲成功 |

## 四、与简历交叉印证的检查点

博客的独特价值在于它是**带时间戳的技术活动记录**，可以和简历互相验证：

| 检查 | 说明 |
| --- | --- |
| 文章主题 vs 简历同期经历 | 时间对得上、主题相关 → 强正向印证 |
| 文章提到的项目 vs 简历项目 | 名称、技术栈、时间是否一致 |
| 文章体现的深度 vs 简历声称的水平 | 简历写"精通"，文章停留在入门 → 值得追问 |
| 简历未写但博客体现的能力 | **加分发现**，提示面试官可挖掘 |
| 文章中的团队/协作描述 vs 简历的个人边界 | 文章说"我们团队"，简历说"独立完成" → 追问 |

**注意**：博客与简历不吻合有大量正常原因——不是所有工作都会写成文章、公司项目不能公开写、兴趣方向与工作方向本就可以不同。**只在存在直接矛盾时才追问，不吻合本身不是信号**。

## 五、绝不核验的内容

看到即跳过，不读、不记、不写入任何笔记或报告：

- 生活记录、旅行、饮食、家庭、感情；
- 健康状况、心理状态；
- 政治观点、宗教信仰、社会议题立场；
- 与他人的私人纠纷或情绪表达；
- 薪资、offer、面试其他公司的记录；
- 任何可用于推断受保护特征的内容。

技术博客常混杂个人内容，这是正常的。核验者的职业操守就体现在**主动跳过**这些内容上。
