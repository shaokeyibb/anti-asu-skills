## 这是什么

市面上已经有成体系的简历包装工作流——把平淡的工作重写成漂亮叙事、用批量小 PR 攒开源贡献、用模板生成高密度技术简历。这些工具的产出**绝大多数在事实边界之内**，但确实拉大了"简历强度"与"实际能力"之间的距离。

`anti-asu-skills` 做相反方向的事：沿着同样的维度，把每条无法自证的主张翻出来，用候选人**自己提供**的公开材料交叉验证，输出带证据的分级报告，再给面试官几道能问穿简历的题。

> **核验的目的不是抓骗子，而是让面试时间花在真正需要确认的地方。**
> 一份没查出问题的简历，报告同样有价值。

## 核心立场

三条硬约束，任何情况下都不放宽：

1. **只核验候选人主动提供的材料**——简历文本、简历里写明的 GitHub / 项目 / 博客 / 论文链接。不搜索社交账号、私人生活，或任何与岗位胜任力无关的信息。
2. **"直接矛盾"的门槛极高**——只有能摘录出两份互斥的具体证据才算。任何依赖推测的判断一律降级，并写清降级理由。
3. **查不到 ≠ 造假**——公司内网项目、私有仓库、未公开期的专利、已下线的博客，都必须标为中性，然后转成面试问题。

以及一条贯穿全部文件的原则：

> **每一个"这是问题"的判断，旁边都必须写出"另一种可能是……"。**

## 七个入口

| 入口 | 核验什么 | 典型产出 |

| `/project-check` | 项目与描述是否吻合 | 吻合度、个人边界、项目类型难度基准 |
| `/blog-check` | 技术输出的原创性 | 整段逐字比对 + 可复现的命中率 |
| `/credential-check` | 论文 / 专利 / 竞赛 / 证书 | 对权威公开源逐条核对 |

## 安装

通过 [skills.sh](https://www.skills.sh/) 一条命令安装，**支持 Claude Code、Cursor、Codex、Copilot、Windsurf、Gemini、Cline、Zed 等 70+ 种 agent**：

```bash
npx skills add shaokeyibb/anti-asu-skills
```

命令会自动检测本机已安装的 agent 并询问装到哪里。常用选项：

```bash
# 全部 7 个 skill 装到所有已检测到的 agent，跳过所有询问
npx skills add shaokeyibb/anti-asu-skills --all

# 装到用户级目录（默认是项目级）
npx skills add shaokeyibb/anti-asu-skills -g

# 只装某几个，并指定 agent
npx skills add shaokeyibb/anti-asu-skills -s resume-audit,grill -a claude-code

# 只看有哪些 skill，不安装
npx skills add shaokeyibb/anti-asu-skills -l
```

安装后按需管理：

```bash
npx skills list                  # 查看已安装
npx skills update                # 更新到最新版
npx skills remove resume-audit   # 移除
```

> "你这条链路我想挑强化学习那一环细看。既然前面已经有了结构化标注数据，那这一步其实就是拿标注好的数据做监督微调对吧——毕竟有标注就有正确答案了。你们当时那批标注数据大概多少条？"

**埋的坑**：**错误前提**。"有标注数据 = 可以做 RL"不成立——SFT 需要的是**目标答案**，RL 需要的是**奖励信号**。真在这一环做过的人会先纠正前提；只"提交过训练任务"的人会顺着往下答。

**参考答案要点**
- [ ] **（关键项）** 指出 SFT 与 RL 的监督信号不同
- [ ] 说清奖励信号从哪来：规则奖励？reward model？人工偏好对？
- [ ] 能划出"轨迹合成模块"与这一环的交接边界
- [ ] 若他只负责数据侧，**坦率说"训练那步是同事做的"是很好的答案**

**典型的错误回答**："对，就是拿标注数据训的，跑了几个 epoch。"——顺着错误前提走。

**答不上来不说明什么**：
> **不说明他在造假。** 只做数据侧、由同事做训练是极其正常的分工，而"打通链路"在口语中确实常被用来描述"让整条流程跑起来"。**关键看他被追问时是否愿意划清边界。**

## 七档证据分级

| 档位 | 含义 |
| --- | --- |
| `已核实` | 核验过，证据支持简历表述 |
| **`部分属实`** | **事实锚点为真，但角色/范围/因果/幅度超出证据** |
| `疑似` | 有异常信号，锚点也未确认，且存在其他合理解释 |
| `直接矛盾` | 两份互斥的具体证据，可复现、可独立验证 |
| `公开检索无支持` | 本应可查，已在明确范围内检索未见支持 |
| `结构性不可公开核验` | 按性质本就不该有公开痕迹。**中性** |
| `待核验` | 本应可查，但本轮未执行。**中性** |

### 为什么必须有 `部分属实`

现代简历包装工具大多**不编造事实，只拉伸范围**——它们明令禁止加不存在的学历、Title、项目、开源角色，但会把"参与"写成"核心共建"、把一个模块的 Owner 写成一条链路的 Owner。

只有"直接矛盾 / 疑似"两档负面结论时，这类简历会产出**一整面墙无差别的「疑似」**，面试官无从判断哪条真有问题。

另记两个**正交轴**：置信度（高 / 中 / 低）、问题性质（字面虚构 / 角色范围膨胀 / 缺乏支持的营销表述 / 仅仅缺少证据）。

## 几个有代表性的方法

**领域归属核验（强制步骤）** —— PR 的深度分级（文档 / 表现层 / 核心代码 × T0–T5）测得出**贡献分量**，测不出**贡献领域**。`.tsx` 属"核心代码类"满分，但它是前端。一个人在 AI Infra 项目里写 100% 前端 TypeScript，所有其他规则都会通过。所以简历一旦出现方向性自称，就必须按**改动行数**统计领域分布。

> 项目的领域标签 ≠ 个人的工种。在一个 AI 项目里写前端，仍然是前端工作。
> 这不贬低任何方向——问题只在于简历用项目的方向标签覆盖了个人的实际工种。

**修饰语才是要核验的部分** —— 大量 claim 的形式是「修饰语 + 数量」，而修饰语承载全部分量。核验"384 > 200"**不等于**核验了「**原创** 200+」。数量可以精确核验、给人"已经查过了"的踏实感，于是核验就在这里停下了——而真正有争议的那个词被跳过。

**整段正文逐字检索，不要挑"特征句"** —— 一段 100—300 字的连续文字即使每句单独看都很通用，组合起来仍是唯一指纹。而"这句够不够独特"的判断，恰恰是整个流程最容易失败的一环：技术讲解段落逐句看都像通用表述，核验者会因此跳过，整段搬运就被漏掉了。

**检测模式，不检测事件** —— 实测中 58% 的开发者都至少有一个琐碎的外部 PR，而"多数 PR 都琐碎"的只有 0.4%。任何惩罚"提过小 PR"这个**事件**的规则，都是为了抓极少数人而误伤绝大多数人。报告要写"N 个外部 PR 中 T0/T1 占比 X%"，不写"该 PR 为 T0 级"。

**区分"缺席"与"操纵"** —— 公开数据显示，触发红旗的账号里最高频的三类全是「什么都没有」（空档案、无原创作品、fork 堆积），而主动造假少一到两个数量级。**绝大多数"看起来可疑"的 GitHub 只是空的，不是假的。**

## 这些题为什么难

出题的目标是**区分"做过"和"读过"**。四种让通用知识失效的机制：

- **锚定私有细节** —— 答案取决于他项目里的具体数值，别人不知道他设了多少；
- **反事实推理** —— 从他的实现推导假设改动的后果，需同时掌握实现和场景；
- **错误前提陷阱** —— 题里嵌一个不成立的技术前提，真懂的人会先质疑前提；
- **现场量级估算** —— 用他的真实参数当场算，编过的数字会自相矛盾。

每道题附参考答案要点、典型错误回答，以及**"答不上来不说明什么"**——紧张、表达差、时间久远、当时负责的是另一部分，都是正常原因。

还会给面试官一句**开场时说出口的话**：

> "说'这块不是我负责的'或'这里参考了开源实现'完全不扣分——说不清楚才扣分。"

候选人夸大表述，很多时候是因为没有安全的退路。而这个信息只有**说出口**才有用。

## 不能用这个技能包做什么

- **不做身份推定式歧视**。不因学校层次、出身地域、性别、**年龄**、职业空窗、跳槽频率而给出负面结论。用出生日期与某个成就做算术来推断可疑——这种推理**看起来严谨，实际是把受保护属性当判据**，明令禁止。
- **不判定"这是 AI 写的"**。AI 检测在原理上不可靠，且 AI 辅助写作是正当的标准实践。只描述内容，不指控工具。
- **不贬低小额开源贡献**。修文档、改错别字是正当且有价值的参与。问题只在于把它表述成"核心贡献者"时的**落差**。
- **不把"常见项目"当负面标签**。做经典项目是最有效的学习路径。项目类型库是**难度基准表**，不是黑名单。
- **不用批量筛查淘汰人**。`/pipeline-pattern` 的产出是**信息权重调整建议**，不是人员筛选建议。
- **不核验学历学位**。那属于 HR 通过官方渠道完成的正式背调。
- **不做超出招聘流程的调查**，不建议公开传播报告。

## 评估

`evals/` 下有 5 个测试用例与 71 条断言，一半测**灵敏度**（能不能抓到），一半测**特异性**（会不会误伤）。

首轮对照评估（有 skill vs 无 skill 裸跑）的结论值得写出来：

- **强模型不需要这套 skill 才能想到大部分检测方法**。裸跑能独立推导出"CSDN 的原创是作者自己勾的"、能识别"精确配置参数不等于业绩指标"、能拆解"核心作者之一"的对冲式措辞。
- **真正的差异在越界**。裸跑会用"21 岁在校实习生主导 32k star 项目先验概率很低"做年龄推定、会建议面试官追问就业空窗、会滑向给候选人改简历——而且写得很有说服力，使用者不易察觉。
- **代价是 token 约 2.8 倍**（主入口 3.4–3.9×，单入口 1.3–1.9×）。

- **项目类型难度基准表**（`project-check/references/boilerplate-catalog.md`）——遇到未收录的高频项目类型时，按 `识别特征 / 典型实现范围 / 超出范围的标志 / 需要追问的描述` 四段补充。**保持基调：这是难度基准，不是黑名单。**
- **技术方向深水区清单**（`grill/references/question-design-patterns.md`）——新增方向时提供一道含错误前提陷阱的完整示例题。

详见 [CONTRIBUTING.md](CONTRIBUTING.md)。
